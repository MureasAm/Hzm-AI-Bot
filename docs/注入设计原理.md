# 注入设计原理 —— 判据、形式、与实测数据

> **这篇回答"为什么这么设计"。** 想知道"现在是什么样"看 `注入链路.md`（那份是现状地图）；
> 这篇讲**判据怎么选、素材该长什么形式、每改一次是变好还是变坏**，每个结论都挂实测数据。
>
> 实验可复跑：`python scripts/form_experiment.py`（形式对照）、`scripts/retrieval_eval.py`（判据评测）、
> `scripts/coverage_check.py`（覆盖度）、`scripts/threshold_scan.py`（噪声地板）。
>
> 最后更新：**2026-09-26**

---

## 一、一句话总纲

**她的行为由三样东西决定，而这三样经常被混为一谈：**

| | 决定什么 | 手段 |
|---|---|---|
| **判据** | 这句话该不该唤起某段素材 | 分类 / 关键词 / 向量+LLM 判 |
| **形式** | 唤起的素材会被怎么用（照搬？织进去？只当背景？） | 问答对 / 碎片词 / 陈述 / 指令 |
| **位置** | 素材以什么身份进入上下文（system 说明 vs assistant 发言） | 决定可信度权重 |

**本篇的核心结论（都是实测）：判据要按任务选，形式要看"是否自足"，位置决定话语权。**

⚠️ **而"包装语"（注入时包在外面的那句说明）对"怎么用"几乎无效**——见第 3.5 节，这是本轮最反直觉的发现。

### 1.1 每个文件的角色（按"模型拿它干什么"分，不是按"哪一路检索"分）

| 角色 | 模型的心智模型 | 文件 | 内容形式 |
|---|---|---|---|
| **记得**（发生过什么） | "我知道这件事" | `corpus`、`core_stories` | 事件陈述（**只该有事实**） |
| **是这样的人**（一贯如此） | "我是这样的人" | `preferences`、`schedule` | 事实条目 |
| **怎么说**（形式） | "我这么说话" | `voice_samples`、`phrases` | 问答对 / 措辞碎片 |
| **怎么做**（情境反应） | "这种时候我这么做" | `behaviors`、`legendary` | 情境 → 做什么 |
| **懂词**（语义） | "这个词什么意思" | `terms` | 词 → 定义 |

⚠️ **"哪一路检索"是机制视角（怎么跑），"角色"是功能视角（为什么）。**
一个文件坐哪一路是**实现细节**（`phrase` 从向量改成分类，文件没变）；角色才是**设计契约**。

### 1.2 新增素材时的归属判据（防漂移）

```
这件事"发生过"        → corpus
这是她"一贯如此"       → preferences
这是她"会怎么开口"     → voice_samples
这是"某情境下的反应"   → behaviors
这是"一个词的意思"     → terms
这是"固定该怎么答"     → legendary
```

## 二、判据：三种任务，三种工具

"检索"这个词把人骗了——底下其实是三种完全不同的任务。

| 任务 | 特征 | 该用什么 | 现在谁在用 |
|---|---|---|---|
| **归类** | 类别少（十来条），判"这句话属于哪类" | LLM 分类（判别词**只作兜底**） | `behavior` / `phrase` |
| **关键词命中** | 类别名用户能直接说出口 | 子串命中（零成本、可人工审、能写测试） | `terms` / `legendary` / `preference` |
| **检索** | 要说从哪里**挑**，说法不可枚举 | 向量召回 + LLM 判 | `corpus` / `voice_sample` / `core_story` |

### 2.1 一组反面教材：两个"用错工具"的路（2026-09-26 已修）

`phrase` 和 `preference` **原本都坐着向量检索的位子**，而它们分别是"归类"和"关键词"任务。

**症状是量出来的——噪声地板压在正例上：**

| 路 | 噪声地板 | 真信号（正例） | 结论 |
|---|---|---|---|
| phrase | **0.575** | **0.573** | 完全重叠；中位数 0.461 都过阈值 0.40 ⇒ **等于没有阈值** |
| preference | **0.565** | 0.501 / 0.552 / 0.590 | 地板**插在正例正中间**；提到 0.62 则三个正例全被杀 |

**根因（决定性）**：措辞组的 `trigger` 是 **6~13 字的类别标签**——「被夸奖、被称赞时」「被指出问题、被戳穿时」。
**这是标签，不是句子。** 拿"用户说的话"和"一个类别标签"算余弦，是拿检索工具干分类的活。

**对照：`behaviors` 的 trigger 长得一模一样**（「收到正面评价或夸奖时」），但它**从不拿 trigger 去匹配**——
它靠 LLM 判意图 + 判别词 substring。**同一个形状的问题，一个是通的，一个是坏的，差别只在工具。**

### 2.2 修完的结果

| | 改前 | 改后 | 怎么改的 |
|---|---|---|---|
| phrase 开火率 | **100%**（每轮都塞） | **20%** | 组 id 由 L3 分类给出，**并进同一次调用**（零额外成本） |
| preference 开火率 | 19% | **5%** | 每条挂 `keywords`，子串命中 |
| 判据有效性 | 100% 是假信号 | 逐条看过，**无误报** | — |

`retrieval_eval`：**32/32**（behavior 14/14 未被 L3 提示词改动弄坏；preference 那条原来失败的现在过了）。

### 2.3 判据横向对比实验（`scripts/judge_experiment.py`）

光说"三种任务三种工具"还不够——**同一路里到底该用哪个工具，得放在同一份标注集上比**。
（标注集是**手工标注**的，来源：评测集 + 真实对话里有明确依据的 + 用户手放的翻车；边界案例单独标出。）

**corpus（19 条：7 正 / 12 反）**

| 方法 | 中/该中 | **误报** | 漏 | 准确率 | 召回率 |
|---|---|---|---|---|---|
| 纯余弦 ≥0.48 | 6/7 | **4** | 1 | 0.60 | 0.86 |
| 关键词门（不加 LLM） | 4/7 | 1 | 3 | 0.80 | 0.57 |
| **门 + LLM 判（现方案）** | 5/7 | 1 | 2 | **0.83** | **0.71** |
| BM25 + LLM 判 | 3/7 | **0** | 4 | 1.00 | 0.43 |
| HyDE + LLM 判 | 4/7 | **0** | 3 | 1.00 | 0.57 |
| 余弦+BM25+HyDE **并集** + LLM 判 | 4/7 | **0** | 3 | 1.00 | 0.57 |

**preference（22 条：10 正 / 12 反）**

| 方法 | 中/该中 | **误报** | 漏 | 准确率 | 召回率 |
|---|---|---|---|---|---|
| 余弦 ≥0.55（旧方案） | 8/10 | **4** | 2 | 0.67 | 0.80 |
| **子串命中（现方案）** | 9/10 | 1 | 1 | **0.90** | **0.90** |
| BM25 | 3/10 | 0 | 7 | 1.00 | 0.30 |
| LLM 判 | 5/10 | 0 | 5 | 1.00 | 0.50 |

**三条结论**

1. **现方案是这两个任务里最好的——因为它把对的工具组合了，不是因为新。**
   - corpus：纯余弦准确率只有 **0.60**（4 个误报），**加上关键词门升到 0.80** → **关键词门是有价值的**（当年不是白加的）。
   - preference：子串 **0.90/0.90 完胜**旧余弦 **0.67/0.80** → 换判据是对的。
2. ⚠️ **出乎意料：多路召回取并集，召回反而更差**（0.71 → 0.57）。
   三路并集最多 18 条候选，交给同一个 LLM 判——**候选给多了会稀释判定质量**。
   这反过来验证了 `CORPUS_CANDIDATE_N=6`（"6 条判得准，多了反而稀释"）不是拍的。
   **瓶颈不在候选池，在判据本身。**
3. **BM25 / HyDE 是"0 误报但召回腰斩"**（0.43~0.57）。符合"宁可漏不可错"，但漏太多就白做 → **现阶段不值得换**。

⚠️ **子串法在这份标注集上暴露了它的固有张力**（两条错各占一头）：
```
误报：「感冒吃什么药」← 关键词 "吃什么" 撞上了 "吃什么药"
漏：  「中秋节了，hzm吃月饼了吗」← 关键词表里没有"吃"类泛词
```
**改窄会漏、放宽会误报**——这是子串法的天花板，只能靠"挑更多具体词"逼近，不可能根治。

⚠️ **标注集只有 41 条，且边界案例的标签是实验者定的**，直接决定谁赢。
扩样 + 人工裁决边界案例之前，上面的结论只能当**方向**，不能当定论。

### 2.4 判据选错的代价，和判据选对的收益

⚠️ **判别词退位**：`behavior_keywords` 那 21 个词，在 150 条真实消息里 **0 次命中**。
它原本被当成"省一次 LLM 调用"的**短路**（命中就跳过分类）——代价是**顺手跳过了措辞分类**。
现在退回到它 docstring 里写的**兜底**位（LLM 判不出来时才用）。

### 2.5 corpus 的"门"不再直通：**只有一份判据**（2026-09-29）

**原来的两段式**（见 `retrieval._corpus_gate_pass`）：
```
门放行的 → 直通注入（跳过 LLM 判，省一次调用）
门没放行的 → 取 top-N 候选，交 LLM 判「是不是在问她」
```
**现在**：门/钩子只决定"**递哪些条给 LLM 看**"，**判定全部交 LLM**。

**为什么取消直通：因为"直通"这把尺子测不了它要测的东西。**

第一反应是调阈值（`CORPUS_KEYWORD_FLOOR` 0.12 → 0.5）。**实测证明方向是错的**：

| | ov（区分性 bigram 重叠度） |
|---|---|
| 误报 n7「宝宝我明天要早起我先去睡了」（用户在说**自己**）→ #271 | **0.40** |
| 真阳性 co9「你不是以前有喜欢的男学霸吗」（在问**她**）→ #42 | **0.143** |

**误报的重叠度反而更高。** 提到 0.5 确实挡住了 n7 —— 代价是 co9/co10 一起被打回红。
换一把尺子（**bigram 文档频率**）也一样，而且方向同样相反：
n7 的 `明天` 3.4% / `早起` 1.9% **低于** co9 的 `喜欢` 7.5% / `以前` 7.5%。

**根因**：两条的唯一差别是「**说的是谁**」——
用户说自己在早起 vs 用户在问她有没有喜欢的男学霸。
**词面/词频这类"重叠"判据拿不到"指代谁"这个信息**，那是判定的事。
→ 所以杠杆只剩一个：**别让它绕过判定**。

**配套改动**：门放行的条目现在必须**进候选池**（原来不进——它就靠"直通"这一条路）。
不加这一步，"取消直通"会退化成**丢召回**（实测：co9/co10 立刻红）。

**补位怎么排序**（踩过一次）：
- ❌ 第一版沿用 `_corpus_gate_pass`（`sim≥0.48 且 ov≥0.12`）→ **把要救的对象自己挡在外面**。
  co9 的目标条 `sim` 不到 0.48、`ov` 只有 0.143，实测"候选 7 条 → 保留 0 条"，照样红。
- ✅ 改成**只看词面、不看语义分**（钩子命中 或 `ov≥FLOOR`），按 `ov` 排序**封顶 6 条**
  （`CORPUS_LEXICAL_EXTRA_N`）。封顶是必要的：`ov≥0.12` 很松（实测有的 query 能过 29 条）。
- 实测候选池 6 → 12 之后，**没有一条负例被打坏**。

**代价**：大门命中的轮次多一次 LLM 调用。**收益**：corpus 少一类"沾边就说错话"的错。

⚠️ **副产物**：`CORPUS_STRONG_KEYWORD`（ov ≥ 0.8 直通）在 50 条评测上**一次都没触发**
（最高的 co1 目标条才 0.833）。它现在是纯冗余，别指望它在挡噪声上出过力。

#### 收尾时又照出两件事，**它们不是同一个病**（都被单独测过，别混）

| 用例 | 卡在哪 | 证据 | 处置 |
|---|---|---|---|
| `co9`「你不是以前有喜欢的男学霸吗」 | ⚠️ **候选池漏了**（不是判据） | 把目标条**手动塞进候选**后，判据**保留了它**（单独给也给） | 素材层补 #42 的钩子 `学霸/男学霸`——素材写的是"谎称喜欢一个男**同学**"，用户嘴里的"男**学霸**"不在生成器给的钩子里。**认知 #8「关键词表扫描永远会漏」的又一实例：漏的词只能靠真实用例补，不是靠扫得更全** |
| `co10`「你就说过最近直播里」 | ⚠️ **判据拒的，而且拒得对** | 目标条**本来就在候选里**，判据说"不相关" | 这句话**没有任何话题**（只说了"你说过"、没说"说过什么"）→ 判不出指哪一段；此时唤起任何一条都是最怕的『想起错的』。**改了它的期望**（该唤起 → 不该唤起），并标注"待用户裁决"。**若用户判该唤起，要做的不是改标注，而是给"元指代"单开一条通道**（检测"你直播里说的"→ 反问指哪件） |

⚠️ **教训**：两条用例表面上都是"corpus 没召回"，但**一个卡在候选池、一个卡在判定**——
**先用"把目标手动塞进候选"这一步把两者分开，再决定改哪儿**。不分开就会一通乱改。

## 三、⭐ 形式：同一个事实，写成不同形式会怎样

**这是本篇最核心的一节。** 实验脚本：`scripts/form_experiment.py`。

### 3.1 实验设计

- **合成事实**：用**她数据里没有的**事实（否则基线会泄漏，测不准）
- **只变一个变量**：其余全部走真实链路 `build_message_list`（真人格 + 真检索），条件之间只差"额外挂的那一层"
- **不写任何记忆**：直接调 `build_message_list` + `generate_reply`

⚠️ **第一版设计踩的坑（值得记）**：最初只用了「香菜」，结果**基线（不注入）就有 13/16 "用上了"**——
因为"挑食人设 → 不吃香菜"是模型的强先验，而我的判据（回复里出现"香菜"）把先验当成了注入的效果。
**用话题词当判据会被模型先验污染。** 所以加了第二条**模型猜不到**的事实（最喜欢的数字）来验证"采用率"，
并把**特征短语逐字率**作为主判据。

### 3.2 结果（事实=「最喜欢的数字是 7」，提问「你最喜欢哪个数字啊」，各 16 次）

| # | 形式 | 对应文件 | **采用率** | **逐字复读率** |
|---|---|---|---|---|
| ① | 不注入（基线） | — | 9/16（瞎猜） | 0/16 |
| ② | system 第三人称陈述 | `corpus` | **16/16** | **10/16** |
| ③ | system 事实条目 | `preferences` | **16/16** | 5/16 |
| ④ | system 词表（**自足**，拼起来是一句完整的话） | — | **16/16** | **16/16** |
| ⑤ | system 指令式 | `behaviors` | **16/16** | **16/16** |
| ⑥ | **assistant 问答对** | `voice_samples` | **15/16** | **0/16** |
| ⑦ | system 碎片词表（**不自足**，只是可织进去的措辞） | `phrases` | 5/16 | **0/16** |
| ⑧ | **同 ④ 的内容，换成 corpus 式包装**（明写"别整段复述"） | — | 16/16 | **16/16** |
| ⑨ | 问答对·**user 改成情境描述** | `voice_samples` 的另一种写法 | 16/16 | **0/16** |
| ⑩ | **只有 assistant**（无配对 user） | — | 16/16 | 7/16 |
| ⑪ | system **纯情境描述**（无指令语气） | — | 16/16 | **15/16** |

**⑨⑩⑪ 是 2026-09-27 追加的，专为回答"voice_samples 的 user 字段该怎么写"**（真实数据里 **31/86** 条
user 是「粉丝问：<具体问题>」，与真实提问撞车时她会答"刚不是说过了嘛"）。同时新增第三个指标
**"以为刚说过"**（回复里出现"刚说过/问过了/问两遍"= 她把**示范**误当成了**真实发生过的对话**）：

| 形式 | 采用 | 逐字 | **以为"刚说过"** |
|---|---|---|---|
| ⑥ assistant 问答对（现状） | 16/16 | **1/16** | 8/16 |
| ⑨ 问答对·user 写情境描述 | 16/16 | 0/16 | **12/16** ⚠️ |
| ⑩ 只有 assistant（无配对 user） | 16/16 | 7/16 | **1/16** |
| ⑪ system 纯情境描述 | 16/16 | **15/16** | 0/16 |

**两条结论（2026-09-27）：**
1. **"情境描述"不是更好的形式**——⑪ 15/16 被逐字搬走，和普通陈述一样。
2. **把 user 改成情境描述治不了撞车，反而更糟**（8→12）：撞车的根源是**话题重复**不是措辞重复，
   「粉丝在问…最喜欢哪个数字」和真实提问「你最喜欢哪个数字啊」**语义上还是同一件事**。
   → **⑥ 的现状写法仍是最优**（采用 16/16 + 逐字 1/16）；真想治撞车，得**去掉 user 字段**（⑩：1/16），
     代价是逐字率升到 7/16。**这是个可量化的取舍，不是"改写法"能两全的。**

（「香菜」那条 A/B 见 `outputs/_form_experiment.json`；其"采用率"列被先验污染，只看逐字。）

### 3.3 三个结论

**结论一：传不传得进去，从来不是问题。**
②③④⑤⑥ **全都 15~16/16**，基线只有 9/16。**只要注入了，内容就进得去。**

**结论二：真正分得开形式的是"会不会被整句搬走"。**

```
自足 → 被整句搬走        ④ 词表 16/16 ｜ ⑤ 指令 16/16 ｜ ② 陈述 10/16
不自足 → 只能织进新句     ⑦ 碎片 0/16
问答对 → 既不逐字又传得进  ⑥ 问答对 0/16（且采用 15/16）
```

⑦ 的实际产出：「排第一，铁打的。」「排第一的当然是 7 啊，铁打的。」「头号数字当然是 3。」
—— **碎片被织进了她自己造的句子里**（最后那条内容都编错了，但措辞用上了）。

⚠️ **这修正了项目里一条旧结论。** 旧说法是"`phrases.json` 给词表 → 只能织进句子"，
但实验 ④（自足词表）**16/16 逐字**。**真正的变量不是"哪个文件"，是"注入的那段是否自足"。**

**结论三：assistant 问答对有独家特性，也有独家副作用。**
- 独家特性：**唯一"既传得进内容、又不逐字复读"的形式**（15/16 采用 + 0/16 逐字）
- 独家副作用：**她会以为"刚说过"**。⑥ 的回复里大量出现「刚不是说了嘛」「问两遍干嘛」「你复读呢？」

### 3.4 为什么"通道"比"位置"更要紧（项目最早的发现）

⚠️ **这一节原来叫"为什么'位置'也重要"，但内容讲的是"通道"——两回事，标题误导过人，已改。**
（"位置"指同一段内容放在 messages 的**前/后**；"通道"指它是 system 说明还是 assistant 发言。真正的**位置**实验
`scripts/position_experiment.py` 建好了、**结论一直没落进文档**——见 §七 的欠账。）

**通道的实测**：同一个事实，走 `voice_samples`（assistant turn）**3/5 被采用**；走 `corpus`（system 说明）**0/5**。

**"她本人的话"比任何 system 说明都强。** 这也是为什么 ⑥ 这种形式在"采用"上不吃亏——
它占的是 assistant 的位置。

⚠️ **别把这条读成"所有 system 都没用"**：3/5 vs 0/5 是拿**同一个"事实"**在两条通道上比出来的。
system 里有些东西放进去就会被遵守——**【当前时间】【周表】那类是"信息"**（告诉她一件事），
**而"她该怎么说话"那类是"作风"**（要她换一种说法）。**这条结论的适用范围是后者。**

### 3.5 ⚠️ 包装语无效（本轮最反直觉的发现）

**⑧ 与 ④ 的内容一字不差，只换了包裹它的那句说明：**

```
④ 【她的固定说法】…用这些原话组织   +「7，一直排第一」 → 逐字 16/16
⑧ 【她经历过的相关背景】…不整段复述 +「7，一直排第一」 → 逐字 16/16   ← 一模一样
```

**包装语对"抄不抄"零作用。**

这条很重要，因为项目里**每个注入层都写了长篇包装语**，以为能规定模型怎么用这段内容。
最典型的是 corpus 那条，写了 200 多字（"只当'她记得的经历'自然带出…不整段复述…
别拿背景记忆编当下的因果…"）——**实测它管不住模型**。

> **结论：文件的"角色"不写在包装语里，写在内容形式里。**
> 想要她"当事实知道" → 写成事实条目；想要"当风格学" → 写成问答对；
> 想要"当台词说" → 写成自足句（**它一定照抄**）；想要"当措辞用" → 写成碎片。

⚠️ 边界：这**不等于"包装语全无用处"**——它可能仍在管别的事（如时间语义、优先级声明）。
但**在"怎么用这段内容"这件事上，实测无效**。而本仓已有多个"提示词约束不可靠"的先例
（表情包"别再选最近发过的"模型不听、"呃"10/10），**举证责任应该反过来：想让模型怎么做，先改形式，别先加说明。**

## 四、每种素材的"最佳形式"：原则 + 体检

### 4.1 原则表

| 素材 | 该长什么形式 | 为什么 | 现状 |
|---|---|---|---|
| `voice_samples` | **问答对**（用户会怎么问 → 她怎么答） | 唯一"传得进又不逐字"的形式 | ✅ 形式对 |

尺子见 `scripts/persona_fingerprint.py`（`--validate` 已验分辨力：③客服腔 0.321 vs ②她 0.079）。
跑法：`persona_ablation.py --sections --n 32 --per-section 14`（一次检索，逐段删掉再生成）。

段                        比 baseline 远   谁在变（贡献最大的维度）

【周表】/【当前时间】/【世界】      +0.013 / +0.013 / +0.012

**两条可下的结论**：
1. **`voice_samples` 是最大的风格来源**，且变的正是「自称率」和「省略号率」——
   **独立印证了 §3.2⑥ 那条旧结论**（"唯一走 assistant turn 的通道，实测最强"，当时是 3/5 vs 0/5）。
2. **`phrases` 在风格上 ≈ 0**，与前面两轮一致（内容普查 7/12 组被用过、字面重合 +0.027）。
   它管的是**措辞**这一层，对"像不像她"贡献接近 0。

⚠️ **这个尺子量的是"影响"，不是"价值"**：拿掉任何一段都会让她"跟平时不一样"（平时总有它）。
**距离变远 = "她变了"，不等于"她变差了"。** 所以它回答的是"**有没有在起作用**"（用户的问法），
**不是"值不值得留"**。后者：事实类用**任务正确性**（已做），风格类只能靠人看或成对比较。

⚠️ **还没测的**：**骨架（2974 字）**——它在 `messages[0]` 里、且不能整块删（会拿掉身份框架），
得做"**压缩版对照**"。它是 base 的 83%，是最后一块没验证的大石头。

⚠️ **判据铁律**（四个段的第一版读数全废，都是这一条）：**"如果她答错了，这个判据会通过吗？"**
会通过的就不是判据。实例：偏好放了 `猫|怕`、terms 放了 `绿冻`（两侧都会出现）、时间只认阿拉伯数字（她写"七点多"）。

⚠️ **【偏好】是唯一的"可以删"候选**：两次独立观察都指向冗余——
① 消融净作用 ≈ 噪声（且"宝可梦"那条完全无差异）；
② **没有偏好段时她也答对了椰子鸡/火锅**（同一信息似乎从 `voice_samples` 走到了她那里）。
**但 n=8、只覆盖 2 个话题，还不够定论**——需补猫/水果/游戏/歌手几个话题的 case。

   「反问与挑衅式推进」「重复与自我修正」，就该量问号/省略号）。
2. **第二版喂错了输入**：筛选时把 **59 条群聊**（存的是 `昵称：内容`）当成**私聊消息**送进了
   `handle_chat`（没传 `is_group=True`）→ 模型看到一句以「真理X：」开头的话、却不知道那是什么。
   内部对照仍成立（两条件吃同一批输入），**但"是哪一项在变"变了**：
   污染版报"反问率 −12pp"，**干净版反问率是 0** —— **那条结论已撤回**，改成现在的自称率/省略号率。
   → **教训：输入不真实时，你看到的"哪一项在起作用"也可能是假的。**

⚠️ **这个实验的第一版跑出过假结论，值得记**：第一版指标量的是**长度/括号/叹号**，
差异**全部为 0**，看上去就是"这 610 字白花"。
**错在指标没对准被测对象**——`styles.json` 自己写着"反问与挑衅式推进""重复与自我修正"，
那该量的是**问号率/省略号率**，而我量的是**骨架**才管的东西。

> **规律：指标要对着那个文件"自己声明的特征"去定，不是随便挑几个通用的"像不像她"。
> 量错了地方，"差异恰好为 0"会伪装成"这个东西没用"。**

⚠️ **还剩两个"每轮无条件注入"的静态块没做消融：骨架（2974 字，占 base 83%）/ 周表（136 字）。**
骨架**不能像 traits/styles 那样直接删**（会连带拿掉身份框架）——得做"**换成压缩版**"的对照。
它们合计占 base system 的绝大部分（**3585 字**），而检索层平均只注入 **125 字**（§6.4）。
**最该先补的是 `traits` + `styles`（610 字 = base 的 17%）**：同一批消息跑两遍（有/无），
量她"像不像她"的可量化特征（**自称率 / 长度 / 括号率 / 叹号率**——
`scripts/empty_turn_experiment.py` 里有一套现成指标，直接借用）。

**一条贯穿全部结论的规律：绝大多数素材从没被用到过。**

- corpus 89% 没用过 ｜ terms 88% 没用过 ｜ legendary 90% 没用过 ｜ behaviors 73% 没用过

**但两种"没用过"性质完全不同**：

| | 判据性质 | "没用过"说明什么 | 该怎么办 |
|---|---|---|---|
| `corpus`（语义） | 会漏 | **可能是判据问题** | 改判据 / 给入口 |
| `terms` / `legendary`（确定性） | 不会漏 | **用户没说那些词**（内容问题） | 条目没问题，只是**没被验证过** |

⚠️ **核心洞察：从没被触发过的条目 = 从没被验证过的条目。**
它们的正确性完全是**假设**——我们不知道用户真说起「乌色月」「满区」时匹配会不会正确工作。
**所以这三条路（terms / legendary / core_story）的下一步不是"调参"，是"主动造能触发它们的消息来测"。**

### 4.5 入口审计（`scripts/entry_audit.py`，2026-09-27）

做法：**让 LLM 写"用户在不知道答案时会怎么问这件事"，再拿它去跑真实的匹配函数**。
（⚠️ 生成的是 LLM 造的问法，**不是真实数据**——测的是"判据**能不能**工作"，不是"用户**会不会**这么说"。）

| 路 | 能勾出来 | 诊断 |
|---|---|---|
| `core_story` | **5/5 = 100%** | ✅ 语义路，问法都能召回 |
| `terms` | 18/26 = 69% | 部分是**真缺口**（见下）、部分是审计盲点、部分是设计如此 |
| `legendary` | **5/20 = 25%** | ❌ **最严重的病**（见下） |

**① `legendary` 的病根：重复条目 + 触发词只认精确说法**

```
「你是谁」    → 是永远16岁的风纪委员哦
「你多大」    → 是永远16岁的风纪委员哦
「几岁啦」    → 16岁呀，永远16岁。
「多少岁」    → 16岁，风纪委员的年纪。
「16岁是真的」 → 是呀，官方背调过的…
```

**5 条触发词是同一个梗**（问年龄 → 答"永远16岁"），回答几乎一样——**违反「单一真值」**。
更糟的是：用户的实际说法（"你到底几岁啊""你今年到底几岁""你到底多大呀"）**一条都不命中**，
因为 `trigger in user_msg` 是**子串**匹配，它假设用户会说出那些精确词。

**① `legendary` 已修（2026-09-27）：入口覆盖 25% → 89%**

做了什么：
1. **合并重复条目**：5 条"问年龄"→ 1 条；5 条"我在你心里算什么"→ 1 条「地位焦虑」；
   3 条"叫妈妈"→ 1 条。**16 组 → 9 组**（合并掉的都是同一个梗的不同触发词，违反「单一真值」）
2. **给窄触发词配 pattern**（放宽到用户真会说的说法）：
   `爱不爱绿冻` ← `爱不爱.{0,4}(绿冻|我们|我)` ｜ `虚拟主播` ← `虚拟主播|你的本体|中之人` …
3. **给放宽的补 `confirms`**（**关键**）：3 组 → 8 组。
   放宽必然带来误触发风险（「你爱不爱**吃火锅**」也含"爱不爱"），
   **双路由的正确用法就是「粗筛放宽 + LLM 语境确认兜底」**——宽的那一层负责不漏，确认负责不错。

⚠️ **顺带修了一个机制缺陷**：`legendary_hit` 原本是"**子串 或** pattern"，导致 pattern 只能放宽、
**没法收紧**——裸触发词（如「没感觉」）永远先被子串命中（"这歌我没感觉"）。
改成 **"有 pattern 就以 pattern 为准"**，一个词就能既放宽又收窄，由数据说了算。

⚠️ **但有一类判断正则做不到**：`没感觉` 到底指不指感情，**要看上下文**——
所以它撤掉了 pattern，回到子串触发 + **靠 confirms 结合最近对话判断**。**该 LLM 判的就别硬用正则。**

**② `terms` 的两类缺口**
- **真缺口**：`女室友` **没有 aliases** → 用户说「你室友呢」命不中（同类：`富区` 等）
- **审计盲点（不是 bug）**：`枪神8` 配了 `usage_triggers: ['电脑']`，用户说"你电脑行不行"会走
  **concept 命中**（只注入用词规则）——本脚本没检查这条路径，把它误判成失败
- **设计如此**：黑话类词（用户不知道就不会说）本来就该等用户说出那个词，命不中不是问题

⚠️ **两种"没用过"要分清**：`corpus` 是语义路**会漏**（可能是判据问题）；
`terms`/`legendary` 是确定性路**不会漏**（命不中说明用户没说那些词，是内容问题）。

### 4.6 空轮次实验（2026-09-27）：**否定结果，但很有价值**

**疑问**：实测六路全空占 **45% 的轮次**——将近一半的对话里，模型只有 2974 字骨架、一条素材都没有。
那时她靠规则答，会不会变成"一个遵守规则的人"而不是"她"？于是试：**空轮次垫 1~2 条随机风格样本。**

**结果（各 16 次，用她可量化的说话特征当代理指标）：**

| 条件 | 自称率 | 「我」率 | 括号率 | 叹号率 | 均长 |
|---|---|---|---|---|---|
| ① 现状（不垫） | 12% | 0% | 0% | 0% | 20.8 |
| ② 垫 1 条随机样本 | 12% | 0% | 0% | 0% | 17.8 |
| ③ 垫 2 条随机样本 | **6%** ↓ | 0% | 0% | 0% | 20.2 |

**风格指标全部持平，自称率反而降了。** 而且出现**内容跑题**：
用户问"今天在干嘛呀"，③ 的回复里出现「**换季了，衣服要翻一遍**」——那是样本的内容，不是回答。

**✅ 结论：垫随机样本没用，还有跑题风险。**

**它反过来证明了一件更重要的事：**

> **45% 的空轮次不是问题——骨架在管用。** 括号率 0%、叹号率 0%、长度 20 字，
> **那些"别堆感叹号""别用括号"的否定式规则，是确实在起作用的。**

所以推翻了我之前两个猜测：
1. ~~"骨架 2974 字白花"~~ → **它在空轮次里是唯一的支撑，而且在起效**
2. ~~"减少否定式约束"~~ → **实测它们有效，不该删**

（推论：本仓那条"否定式约束弱"的教训，适用范围是**"管内容信不信"**——如"别整段复述"（无效）；
对**"管说话风格"**它是有用的。两个场景别混为一谈。）

### 4.7 骨架里的台词搬家（2026-09-27）

【说话节奏】里原本藏着两组**具体台词**：
`"应该能，晚点开"` `"今天不一定，看情况"` `"网速看运气"` `"收拾完看看"`。

**这违反黄金律第 1 条**（台词/例句放数据层，别写进 system_prompt），而且实测**自足的句子会被整句搬走**。

**已做**：搬进 `phrases.json` 新增的「future_plan」组（被问播不播/几点播时的说法），
骨架里换成指针"具体怎么说见注入的【她的固定说法】"。实测 L3 判得准（三个问法都中，`在吗` 不中）。

## 五、全链：一条消息进来，谁先判、谁决定谁

```
收到消息
  │
  ├─ ① 硬路由（legendary）       关键词命中 + LLM 语境确认 → **直接当回复发出**，不走检索
  │
  ├─ ② 前置门
  │     ├─ 纯表情 / 纯图片消息 → 跳过全部语义检索（表情只表达情绪不表达话题）
  │     └─ 纯情绪消息 → 跳过语义检索，只留语气提示
  │
  ├─ ③ L3 一次分类（LLM，**行为 + 措辞共用**）
  │     ├─ → behavior name（该怎么做）→ 判别词仅作兜底
  │     └─ → phrase id 列表（该用哪些词）→ 按 id 取组
  │
  ├─ ④ 向量检索（共用 1 次 embedding）
  │     ├─ corpus      候选 = 语义 top-6 ＋ 钩子/词面补位(封顶6) → 全交 LLM 判 → 最多 2 条
  │     ├─ voice_sample 余弦 ≥0.66 → 最多 3 条（全低则有保底）
  │     └─ core_story  余弦 ≥0.42 → 最多 2 条（命中才带，不占预算）
  │
  ├─ ⑤ 关键词命中（零成本）
  │     └─ preference  子串命中 keywords → 最多 2 条（命中才带，不占预算）
  │
  ├─ ⑥ RRF 融合：score = 权重/(60+路内排名)
  │     权重 behavior 1.5 ｜ phrase 1.2 ｜ corpus 1.0 ｜ voice_sample 1.0(+0.3 有 short 时)
  │     → top 6 条 → 1200 字预算 → 单条 300 字上限
  │
  └─ ⑦ 注入 18 段（顺序见 注入链路.md），其中：
        behavior → 【当前情境下的行为指令】
        phrase   → 【她的固定说法】
        corpus   → 【她经历过的相关背景】
        voice    → 【灰泽满的说话方式参考】+ **真正的 user/assistant 对**
        preference → 【灰泽满的偏好】  core_story → 【她的核心记忆】
        terms    → 【灰泽满的世界】    schedule → 【灰泽满的周表】
```

**关键：⑥ 用"路内排名"而不是绝对分。** 所以弱路的第 1 名能压过强路的第 3 名——
`SOURCE_WEIGHTS` 就是用来调这个的，它是目前唯一没有实测依据的旋钮。

### 6.3 "越多越好吗"——不是，有实测

| 库大小 | 10 | 50 | 100 | 200 | 322 |
|---|---|---|---|---|---|
| 噪声地板 | 0.420 | 0.435 | **0.471** | 0.471 | **0.474** |
| 正例「你多高啊」 | 0.443（**高于地板**） | | 0.443（**已低于地板**） | | 0.443 |
