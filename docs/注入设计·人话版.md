# 灰泽满是怎么回复的

> ⚠️ **2026-10-04 架构重构说明**：`core/traits.json` / `core/styles.json` / `speech/phrases.json` /
> `speech/voice_samples.json` **四个文件已拆掉**（内容并进骨架与 `behavior/behaviors.json`）。
> **本文是历史记录**，其中凡提到这四个文件的段落都反映重构前的状态，**不要按它改回去**。
> 现状与新的分类口径（人格/事实、四种判定方式）看 **`注入链路.md`**。

这是一份从零开始的说明。

只需要先记住一句话：

**模型看到的是 messages，不是文件。**

项目会先从文件里取内容，再把内容变成 system、user、assistant 消息，最后交给模型生成回复。

本文重点讲中间最重要的部分：

1. 用户消息怎样进入系统。
2. 系统怎样取出素材。
3. persona 文件怎样按注入顺序进入 messages。
4. 最终 messages 由哪些部分组成。

最后更新：**2026-10-01**。

---

## 一、先理解模型看见了什么

LLM 每一轮只能看到一串消息。

| role | 意思 | 项目里放什么 |
|---|---|---|
| `system` | 背景、规则、资料 | 人设、周表、记忆、检索结果 |
| `user` | 用户说的话 | 当前用户消息，或样本里的提问 |
| `assistant` | 灰泽满说过的话 | 真人说话样本里的回复 |

例如周表：

```text
persona/world/schedule.json
        ↓ 代码读取并转换成文字
system: 【灰泽满的周表】周三 19:00……
```

模型不会看到 JSON，也不会看到目录。

它只会看到一段叫【灰泽满的周表】的 system 文本。

所以：

```text
文件是维护单位。
messages 才是模型实际接收的内容。
```

## 二、一条消息的 9 步旅程

| # | 阶段 | 做什么 |
|---|---|---|
| 1 | 收到 | 取出文字、@、引用、转发、图片、QQ 表情 |
| 2 | 攒批 | 等 5 到 10 秒，把连续几条消息合成一批 |
| 3 | 理解 | 图片转文字，多条消息先归纳 |
| 4 | 取素材 | 两路 RRF + 两路命中直达 |
| 5 | 组装 | 拼成 17 个逻辑注入段 |
| 6 | 生成 | 交给 DeepSeek 生成回复 |
| 7 | 后处理 | 去括号、清省略号、防复读、拆句 |
| 8 | 发送 | 语音优先，否则分批发文字，最后可能补表情 |
| 9 | 回写 | 更新短期、长期、会话和群记忆 |

前 3 步是在准备“发生了什么”。

中间第 4、5 步是本文重点。

后 4 步是在处理“模型已经生成的那句话”。

## 三、进入注入前的准备

### 3.1 私聊和群聊先分别攒批

每条消息不会立刻回复。

私聊按用户开读秒窗口。

群聊按群开读秒窗口。

用户连着发几条时，系统会等他安静下来，把这几条一起处理。

### 3.2 图片和多条消息先变成文字

图片会被视觉模型描述成文字。

一批消息会先被归纳成 `batch_summary`。

群聊还会给每条消息加发送者昵称。

### 3.3 群聊先决定要不要开口

群聊不是每条都接。

| 情况 | 结果 |
|---|---|
| 点名、@她、引用她 | 必接 |
| 有人表达情绪 | 可以接 |
| 有人分享经历 | 偶尔接 |
| 纯事件 | 小概率接 |
| 纯事务、附和、收尾 | 通常不接 |

判定不接时，不生成回复，但这批消息仍写入短期记忆。

### 3.4 全程注入的只有骨架（人格层的一半）

进入检索之前，只有骨架一个文件无条件进入第一条 system：

| 文件 | 作用 |
|---|---|
| `persona/core/system_prompt.txt` | 身份框架、自我称呼、说话节奏、字数纪律、括号规则 |

代码合成：

```text
system: system_prompt.txt   ← 3452 字，占整轮输入的 91%
```

它不依赖检索，也不依赖命中。**即使后面全部为空，她仍然是"她"。**

> **人格层的另一半是 `behavior/behaviors.json`**——但它**不是常驻**，
> 由 L3 判出情景才注入（16 条里命中哪条注哪条，含那条的真实原句）。
> 实测：「在吗」「我最近好累啊」这类普通闲聊**一个行为都命中不了**，
> 整轮 3802 字里只有 350 字是"当下相关"的。

### 事实层（回答她知道什么）

| 4 | world/preferences.json | **关键词** | 类别 + 稳定事实 |

下面按注入顺序逐项说明。

### 4.1 三个全程注入的人格文件

#### `core/system_prompt.txt`

它是人格骨架，决定：

- 她是谁；
- 怎么自称；
- 什么样的表达绝对不做；
- 括号、停顿和整体说话底线。

每轮都会成为第 1 段 system。

#### `behavior/behaviors.json`（人格层的另一半）

16 条"**情景 → 反应 + 真实原句**"。**不是常驻**，由 L3 判出情景才注入。

- 判定：**LLM 分类**（`classify_l3`，一次调用同时判行为 + 措辞组 + 连续索要），
  判别不到时用 `behavior_keywords.json` 的关键词兜底。
- 形式：`【当前情境下的行为指令】` + 该条的情景/反应/samples。

> `core/traits.json` / `core/styles.json` 两节已删——两个文件已拆，
> 内容分别并进了骨架（反问推进、篇幅纪律）和 behaviors（情景条目）。

### 4.2 周表：`world/schedule.json`

判别：`weekly` 存在就每轮注入。

通道：system。

形式：每周固定安排表。

进入第 2 段，用于回答“哪天播、几点播”等客观问题。

### 4.3 偏好：`world/preferences.json`

判别：`keywords` 子串或 `pattern` 正则命中。

通道：system。

形式：类别 + 稳定事实。

命中后进入第 3 段，不进入 RRF，不占前 6 条名额。

### 4.4 核心记忆：`world/core_story_vectors.json`

这是运行时向量缓存。

判别：与用户消息的向量相似度达到低阈值。

通道：system。

形式：经历陈述。

命中后进入第 4 段，不占 RRF 名额。

### 4.5 名词库：`world/terms.json`

判别：always、关键词、别名或正则。

通道：system。

形式：词义 + 态度 + 用词规则。

命中后进入第 6 段。

含 `confirm: true` 的词条会先经过一次语境确认。

### 4.6 行为：`behavior/behaviors.json`

判别：L3 分类；L3 不确定时由关键词兜底。

通道：system。

形式：情境 + 动作 + 内嵌真人样本。

最多 1 条，进入第 9 段。

真人样本是 system 文本的一部分，不是独立 assistant 消息。

### 4.7 直播经历：`world/corpus_vectors.json`

这是运行时向量缓存。

判别：

1. 向量召回候选；
2. 词面重叠补充候选；
3. LLM 判断“用户是不是在问她这件事”。

通道：system。

形式：第三人称事件陈述。

最多 2 条，进入第 10 段，并参与 RRF。

### 4.8 ⛔ 已删的两节

- speech/phrases.json（措辞）：源文件已删，情景组并进 behaviors。
- speech/voice_samples.json（说话样本）：**整条通道已删**，原因见 注入链路.md 6.1。
  该留的 18 条已并入 behaviors 的 samples。

## 五、两路 RRF 和两路直达

```text
进入 RRF 的两路：
corpus_vectors.json / behaviors.json

命中后直达的两路：
preferences.json / core_story_vectors.json
```

RRF 融合后：

```text
最多保留 6 条
总字符不超过 1200
单条不超过 300 字
```

preferences 和 core_story 不占这 6 个名额。

## 六、最终 messages 的 17 个逻辑段

代码入口：

```python
build_message_list()
```

“17 段”是逻辑层数。

voice sample 会展开成多条 user/assistant 消息，所以实际 `messages` 通常多于 17 条。

| # | role | 内容 | 何时出现 |
|---|---|---|---|
| 1 | system | base：骨架 + traits + styles | 总是 |
| 2 | system | 【灰泽满的周表】 | 有周表 |
| 3 | system | 【灰泽满的偏好】 | 偏好命中 |
| 4 | system | 【她的核心记忆】 | 核心记忆命中 |
| 5 | system | 【群聊现场】 | 群聊 |
| 6 | system | 【灰泽满的世界】 | terms 命中或 always |
| 7 | system | 【当前会话】或【上次聊过】 | 有会话语境 |
| 8 | system | 【当前时间】 | 总是 |
| 9 | system | 【当前情境下的行为指令】 | behavior 命中 |
| 10 | system | 【她经历过的相关背景】 | corpus 判定保留 |
| 11 | system | 【关于这个绿冻的长期记忆】 | 私聊且有记忆 |
| 12 | system | 【最近对话记录】+ 防矛盾和防复读 | 有短期历史 |
| 13 | system | 【她的固定说法】 | phrase 命中 |
| 14 | system | 【灰泽满的说话方式参考】+ 真人对白 | voice sample 命中 |
| 15 | system | 【这批消息的归纳】 | 一批超过一条 |
| 16 | system | 【用户这条消息的语境】或【用户发了表情】 | 短消息/表情 |
| 17 | user | 用户真正说的那句话 | 总是 |

### 6.1 这 17 段分成五组

| 组 | 段落 | 管什么 |
|---|---|---|
| 基础人格 | 1 | 她是谁、怎么说话 |
| 当前事实 | 2、8 | 周表、时间、天气、直播状态 |
| 按需素材 | 3、4、6、10、13、14 | 偏好、记忆、名词、经历、措辞、语气 |
| 对话记忆 | 5、7、11、12、15 | 群现场、会话、长期、短期、批量归纳 |
| 当前输入 | 16、17 | 短消息含义、图片、表情、用户原话 |

### 6.2 system 和 assistant 的区别

system 是在告诉模型：

```text
这种情况她应该怎么做
```

assistant 是在给模型看：

```text
她以前真的这样说过
```

两者都会影响输出，但 assistant 更像直接示范。

### 6.3 为什么顺序重要

```text
越靠前 → 越像长期背景
越靠后 → 越像刚刚发生的事
```

所以人格放最前，记忆和素材放中间，当前用户消息放最后。

## 七、三个例子

### 例子 A：普通闲聊

用户：

```text
今天在干嘛呀
```

最终可能只有：

```text
system: base 人格
system: 周表
system: 当前时间
system: 最近对话
user: 今天在干嘛呀
```

没有命中经历、行为或说话样本，属于正常情况。

### 例子 B：问事实

用户：

```text
你多高啊
```

中间可能多出：

```text
system: 【她经历过的相关背景】
灰泽满被问到身高，说自己1米6……
```

如果还命中说话样本，后面会再出现：

```text
system: 【灰泽满的说话方式参考】
user: ……
assistant: ……
```

corpus 负责事实，voice sample 负责说话方式。

### 例子 C：群聊

除了普通内容，还会多：

```text
system: 【群聊现场】
在场成员：……
群内近况：……
```

而且生成前要先通过群聊接话门。

## 八、五条最重要的设计规则

1. **判据按任务选**

```text
归类 → LLM 分类
关键词 → 子串命中
说法不可枚举 → 向量 + LLM 判断
```

2. **形式决定会不会被照搬**

```text
完整句子 → 容易整句照搬
碎片词 → 更容易织进新句
问答对 → 既能学会，又不容易整句照抄
```

3. **assistant 示例比说明强**

```text
“她不爱自夸”
不如
assistant: 也没有啦，别夸。
```

4. **包装语管不住模型**

写“不要照抄”往往没用，改素材形式更可靠。

5. **先有触发，再谈内容**

没有命中入口的素材，再写得好也不会进入模型。

## 九、最后用一句话记住

```text
用户说一句话
→ 系统判断这句话的情境
→ 两路走 RRF 找候选，两路特殊素材命中后直达
→ 用关键词、分类、向量和 LLM 筛小
→ 按固定顺序拼成 messages
→ 只有 voice sample 会变成真正的 user/assistant 对白
→ 模型生成回复
→ 代码再清洗、发送、写记忆
```

理解这个项目，最重要的不是背文件目录，而是理解：

```text
文件 → 触发判断 → 检索筛选 → messages 组装 → 模型生成
```
