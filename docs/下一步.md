## 待实现：记忆与短 query（2026-10-20 诊断，用户 2151983431）

**现象**：每天早上的「跑步/早操」对话，长期记忆里有
`morning_running：每天早上要去跑早操（校园跑），学校要求的`（confirmed），但「跑步」那轮
被扩写成「用户说自己去跑步了」后，这条事实相关度只有 0.125，和时差/高考两条并列，
排第 5 被「每轮只取 4 条」截掉 → 她当成新发生的事。

**⚠️ 前置 bug（2026-10-20 后台日志确认）：被打断的批次会丢消息**
- 现象：06:22:41「跑步呀」进来并读完秒开始回复；06:22:47「你忘了吗」进来时，
  旧的 `_process` 被取消，而 `_flush` 开头已经把「跑步呀」从 `pending` 里取走了
  （`msgs, win.pending = win.pending, []`）→ **「跑步呀」被静默丢弃**：
  没进短期记忆、没进 chat_log，下一轮「你忘了吗」只看得到「早」。
- 这也解释了为什么聊天记录里搜不到「跑步呀」——只有真正回复过的轮次才会落盘。
- 修法：`_flush` 先取快照 `msgs = list(win.pending)`，**回复生成并记入短期记忆之后**
  才把这一批从 `pending` 里删掉；中途被取消就留着，下一批（含新消息）一起处理。
  群聊“这批不接”的分支同样在记完再删。
- 验收：新增用例——A 开始回复后中途 enqueue B，下一次 flush 必须同时看到 A+B，
  且 A 出现在短期记忆/聊天记录里；不能只看到 B。
- 影响：修掉之前，任何「说了第一句、几秒后追第二句」的场景都可能丢第一句，
  探测/记忆再强也没用（它根本没见过那句话）。

**根因（已量化）**
1. 扩写句里的泛词「用户 / 自己」让无关事实各拿到 1 个二字组（各 0.125），把真正相关的挤下去。
2. `_fact_relevance` 的单字兜底对**长扩写句**也生效，长句靠「用/户」蹭分；它本来只为短消息设计。
3. 探测看不到长期记忆和当前时间：`你忘了吗` 只能扩成「忘了什么事」，不可能点名跑操；
   把全部事实+时间喂给探测会乱猜（实测会猜成“体检”）。
4. 真实日志里「你忘了吗」之前本应有「跑步呀」——它被上面的丢消息 bug 吞了。
   真正攒批时探测能连上（「跑步呀
你忘了吗」两种顺序 3/3 都扩成「提醒之前约好去跑步的事」）。

**方案（按优先级）**
- **A. 事实相关度去泛词**（`memory_v2._fact_relevance`）：算相关度前剔掉查询里的
  用户/自己/对方/今天/现在/什么/这个/那个/事情/之前/说过 等泛词；单字兜底只对 ≤4 字短查询生效。
  实测：「用户说自己去跑步了」→ 跑步 0.25、其余 0；「早安/早上好/跑操」仍命中；
  「在吗/今天午饭吃的啥」仍为 0。
- **B. 当前时段固定事实**（新机制）：按时段挑 1~2 条事实（早上→跑操/体检；晚上→晚自习…）
  进 profile 块，和查询相关度无关。实测「你忘了吗」从 3/3 空话变成 2/3 说出「体检/早操」。
  这是「你忘了吗」这一轮最稳的解，不依赖探测猜。
- **C. 探测上下文增强**：探测目前只拿最近 8 条短期记忆 + 上一轮话题；
  改成拿全短期记忆（10 条）+ 会话事件 + 当前时间，扩写规则加三条：
  ① 提醒/指代要**锚定最近一句或当前话题**，不许只写“某件事”；
  ② 保留用户原词（「跑步」不换成“正在跑步”）；
  ③ 能从已知固定事实对上就写出来，对不上就写“某件之前说过的事”，**不要编**。
- **D. 可选数据**：`morning_running` 的值补上“跑步”二字（用户自己的说法），
  让各种扩写变体都能命中。

**验收**
- 单元：用该用户的真实事实快照测相关度排序（扩写变体 → morning_running 必须入选）。
- A/B：该用户 06:22~06:24 三轮真实对话，改前/改后各生成 3 次；
  预期从「跑什么步啊 / 能忘什么啊」变成「又去跑早操 / 不就是体检和早操嘛」。
- `pytest -q`；记忆相关用例；`retrieval-eval` 不受影响（不覆盖 memory）。
- 风险：B 按时段注入要防止误触发（只按时段词匹配、上限 2 条）；C 只用于锚定，不强制点名具体事实。
