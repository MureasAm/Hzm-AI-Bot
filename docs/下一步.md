## 1. 群聊接话链路：信息不全 + 接不到同一条线上

### 现象

- 接话时**不知道大家在聊什么**就开口；
- 后续聊天**不在一条线上**，像各说各的。

### 现状链路（先认路）

| 步骤 | 位置 | 现在做什么 | 问题 |
|---|---|---|---|
| 攒批 | `chat_window._flush` 群分支 | 把一批消息拼成 `昵称：文本` | 只给**本批**，没有“这批之前”的上下文 |
| 归纳 | `summarize_batch([(t, imgs)])` | 归纳整批说了什么 | **丢掉了发言人**，看不出谁在对谁说、有几条线 |
| 群记忆 | `group_memory` | 在场成员 + 最近事件（有冷却） | 事件级，不是“当前话头” |
| 接话门 | `should_reply_in_group(client, hist[-8:], combined)` | 看最近 8 行 + 本批决定接不接 | 看不到本批的**对话线**，容易接错或漏接 |
| 注入 | `build_message_list` | 群块 + `address_note` + 最近记录 + 本批 transcript | 本批和前文是两块，模型对不上 |
| 落盘 | `append_user_history(群号, _clean_group_record(combined), reply)` | 存成 `用户：A：…\nB：…` | 发言人结构被压平；她的回复**没记“回的是谁”** |

### 方案（按优先级）

**① 批归纳带上发言人 + 对话线（先做，最便宜）**
- 新函数 `summarize_group_batch(items)`（或在 `summarize_batch` 加 `group=True`），输入 `(昵称, 文本, 图片描述)`；
- 输出 1–3 句：**谁在对谁说什么、这批有几条线、最后停在什么话头上**；
- 作为 `group_thread_note` 注入群块，不额外加调用（复用现有那次归纳）。

**② 补“本批前情”**
- 在群分支取最近 6–8 行**本批之前**的记录，作为 `【群聊前文】` 单独注入；
- 和现有 10 行 `【最近对话记录】` 二选一或都保留，做 A/B（群历史 10 行 vs 16 行 vs 前情块）。

**③ 群历史格式**
- 群聊落盘从 `用户：A：…\nB：…` 改成 `群聊：A：…\nB：…`，她的回复记成 `灰泽满（回 A）：…`；
- `get_user_history` 的“谁说的”判断要兼容 `群聊：` 前缀；
- 这样下一批能看到“她上一条在回谁”，而不是只看到她说了什么。

**④ 接话门看“线”而不是只看本批**
- `should_reply_in_group` 增加 `thread_note` 参数（① 的输出 + 上一批的 thread_note）；
- 判据不变，只补上下文；不改 `GROUP_GATE` 开关。

### 验收

- 20 批真实群聊回放（`data/chat_log` 里挑有 3 人以上发言的批次）；
- 指标：
  - **接话是否在聊同一件事**（人工 0/1，目标 ≥70%）；
  - **无主语的“你”被误认成她**的比例（改前 vs 改后，不能上升）；
  - **该接没接**的比例（不能为了少误判变成不接话）；
  - 私聊回归：一对一场景不被群聊文案污染（`pytest` + `run_tool regression --check`）。
- 命令：`pytest -q`、`run_tool retrieval-eval`、`run_tool regression --check`。

### 待讨论

- 群历史窗口到底给 10 行还是 16 行；前情块和最近记录是否重复；
- 她的回复要不要记“回的是谁”（会改历史格式，需回归）；
- 归纳升级会不会让群接话变慢（现在每批已经有 1 次归纳 + 1 次接话门）。

## 2. 长期记忆里的名字：5 轮内出现过就提醒这轮别叫

### 现状

- 名字来源：`_user_name_for(user_id)`（V2 的 `preferred_name` / `name` / `nickname`）；
- 现有守卫 `starts_with_name`：只在**回复已经以名字开头**、且最近 2 条 bot 回复也这样时，才重生成；
- **没有前置提醒**，所以模型每轮都可能先叫一次。

### 方案

**① 新函数 `name_budget_note(user_id)`**（放 `core.py` 或 `memory_v2.py`）
- `name = _user_name_for(user_id)`；空则返回空串；
- 取 `get_user_history(user_id)[-10:]`（5 轮），统计名字出现次数；
- 达到阈值时返回一条系统提示：
  `【称呼】最近 5 轮里已经叫过他「{name}」{n} 次，这轮不要再叫名字，直接说事。`
- 注入位置：`profile_context` 之后、用户消息之前（或写进 `03_profile/block.json` 的 `strings`）。

**② 阈值先做三档 A/B**
- 档 1：5 轮内出现 ≥1 次就提醒；
- 档 2：≥2 次才提醒；
- 档 3：只有最近 2 条 **bot 回复**里出现才提醒（最保守）。
- 指标：名字使用率、名字开头率、回复是否仍然自然（是否完全不称呼、变得生硬）。

**③ 现有守卫保留**
- 若前置提醒不够，再把 `starts_with_name` 的回看窗口从 2 条放宽到 5 条（后置兜底，不替代前置）。

### 验收

- 20 条真实私聊（历史里名字出现过），A/B 三档 + 基线；
- 名字使用率目标：相对基线降 50% 以上，且不出现“整段完全不称呼”的僵硬回复；
- 群聊不受影响（`_user_name_for(群号)` 为空，天然跳过）。

### 待讨论

- 统计时算**她自己的回复**，还是连用户消息里提到的名字也算？用户消息里叫“灰泽满”并不等于她要叫对方的名字，建议只算 bot 行；
- 阈值用“次数”还是“轮数”；
- 提醒语气用“不要再叫”还是“这轮尽量别叫”，后者更软。

## 3. terms 补词：养 / 暴力养 / 娘养 / 满考子

### 暂定释义（**待你确认**，确认后再写进 terms.json）

| 词 | 暂定意思 | 语气/用法 |
|---|---|---|
| **养** | 粉丝圈里长期投入时间、钱或情感去支持、看着主播成长（“养成”）；也用于“养你/养她”的玩笑，不是字面饲养 | 亲昵、调侃；被说“养你”时可以嘴硬回“你先养活自己” |
| **暴力养** | 用力过猛、砸钱/礼物/密集投喂式的“养”，带调侃；不是真暴力 | 夸张玩笑；她可以吐槽“灰泽满又不是盆栽” |
| **娘养** | 像妈妈一样照顾、宠溺、操心（妈粉式），和“爹养”相对 | 亲昵/起哄；她可以嘴硬“什么时候娘养过你” |
| **满考子** | 由“孝子”戏谑成“考子”，前面加“满”指灰泽满；字面“对灰泽满很孝顺”，实际指很喜爱、死忠捧场，带自嘲/调侃 | 自称/起哄；她可以嫌弃“这外号不认” |

### 实现要点

- 写入 `persona/injection/07_terms/terms.json`，`category: "slang"`、`priority: "on-demand"`；
- **“养”不能直接当 keyword**（会撞“养生/养成/养宠物/保养”），要用 `pattern` + `confirm: true`：
  例：`养(你|她|灰泽满|主播|管人|vup|虚拟主播|孩子)`，或 `(?<![生保培])养(?!生|成|老|育|殖|护|家|宠物|猫|狗|花|草)`；
- `暴力养`、`娘养`、`满考子` 用多字 keyword（安全）；`满考子` 可加 alias `满孝子`；
- 每条写 `meaning` + `reaction`，风格参考 `满区` 条。

### 验收

- `run_tool retrieval-eval` terms 路：4 个词各 2 条正例 + 3 条负例（养生/养成/养宠物/保养/抚养）；
- `run_tool problems --query "要养就暴力养"` 看注入实况；
- 真实聊天抽 5 条含词的记录，确认“词义对、态度像她”；
- `pytest -q`。

### 待讨论

- 四个词的释义是否准确，尤其“娘养”是妈粉式照顾还是别的；
- “养”的 pattern 会不会误触“养成系/养号/养蛊”；
- “满考子”是否只用于粉丝自称，还是也能用来叫她。
