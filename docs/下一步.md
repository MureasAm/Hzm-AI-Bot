## 1. 群聊：代码注入 + 提示词一起改

### 现象

- 接话时**不知道大家在聊什么**就开口；后续聊天**不在一条线上**。
- 模型偶尔输出「没点灰泽满名字，灰泽满不回复」这类**元回复**（`is_meta_silence` 能拦一部分，但根子在注入）。

### 根因（代码 + 提示词一起看）

1. `chat_window._flush` 的 `summarize_batch([(t, imgs)])` **丢掉了发言人**，归纳写不出“谁在对谁说、这批有几条线”。
2. `06_group` 的 main 写“点名或 @ 才是直接跟她说；其余是群友互聊，她偶尔可以插一句”——把“是否被点名”当成了说话前提。
3. 未点名时仍注入 `group_address_note = "本批无人点名灰泽满：以上都是群友在互相聊。"`——模型会把这句当成可复述的元信息，偶尔原样吐出来。
4. 群历史落盘 `用户：A：…
B：…`，发言人结构被压平；她的回复没记“回的是谁”。
5. 接话门只看 `hist[-8:] + 本批`，看不到对话线。

### 方案（代码与提示词配套）

**A. 不再注入“无人点名”**
- `_flush`：只有 `batch_addressed` 为真时才构造 `group_address_note`；未点名传空串。
- `build_message_list`：空串不注入；`06_group` 的 `address_note` 只写正向（“A 在跟你说话”）。
- 提示词加一条：**不要在回复里提“点名/没点名/被@/潜水/说不说”**，直接接话或保持安静由门决定。

**B. 群块改写**
- main 从“点名才是直接跟她说”改成“这是多人群聊：有人直接问你，就正面回；没人直接问，也可以顺着话题接一句。不用声明自己在不在被点名。”
- 删掉“其余是群友互聊”这种元信息式表述，改成“群里同时有好几个绿冻，别把别人的话算到她头上”。

**C. 批归纳带发言人/对话线**
- 新 `summarize_group_batch(items)`（或在 `summarize_batch` 加 `group=True`），输入 `(昵称, 文本, 图片)`；
- 输出：谁在对谁说什么、这批有几条线、最后停在什么话头上；
- 作为 `group_thread_note` 注入群块，复用现有那次调用，不额外加调用。

**D. 前情 + 历史**
- 补 `【群聊前文】`：本批之前最近 6–8 行；与 10/16 行历史做 A/B。
- 群历史改 `群聊：A：…` + `灰泽满（回 A）：…`；`get_user_history` 兼容新前缀。

**E. 接话门**
- `should_reply_in_group` 增加 `thread_note`（C 的输出 + 上一批的 thread_note），判据不变。

### 验收

- 20 批真实群聊：
  - 元回复（“没点我/潜水/不回复”）**0 条**；
  - 接话在同一话题 ≥70%；
  - 该接没接率不上升；
  - 私聊回归不受影响。
- 命令：`pytest -q`、`run_tool regression --check`、`run_tool retrieval-eval`。

### 待讨论

- 群历史窗口 10 vs 16；前情块与最近记录是否重复；
- 归纳升级的延迟（每批已有归纳 + 接话门两次调用）；
- `is_meta_silence` 保留为兜底，是否再加“不关我事”变体。

## 2. 长期记忆里的名字：5 轮内出现过就提醒这轮别叫

### 现状

- 名字来源：`_user_name_for(user_id)`（V2 的 `preferred_name` / `name` / `nickname`）；
- 现有守卫 `starts_with_name`：只在**回复已经以名字开头**、且最近 2 条 bot 回复也这样时，才重生成；
- **没有前置提醒**，所以模型每轮都可能先叫一次。

### 方案

**① 新函数 `name_budget_note(user_id)`**（放 `core.py` 或 `memory_v2.py`）
- `name = _user_name_for(user_id)`；空则返回空串；
- 取 `get_user_history(user_id)[-10:]`（5 轮），统计名字出现次数；
- 达到阈值时返回一条系统提示：
  `【称呼】最近 5 轮里已经叫过他「{name}」{n} 次，这轮不要再叫名字，直接说事。`
- 注入位置：`profile_context` 之后、用户消息之前（或写进 `03_profile/block.json` 的 `strings`）。

**② 阈值先做三档 A/B**
- 档 1：5 轮内出现 ≥1 次就提醒；
- 档 2：≥2 次才提醒；
- 档 3：只有最近 2 条 **bot 回复**里出现才提醒（最保守）。
- 指标：名字使用率、名字开头率、回复是否仍然自然（是否完全不称呼、变得生硬）。

**③ 现有守卫保留**
- 若前置提醒不够，再把 `starts_with_name` 的回看窗口从 2 条放宽到 5 条（后置兜底，不替代前置）。

### 验收

- 20 条真实私聊（历史里名字出现过），A/B 三档 + 基线；
- 名字使用率目标：相对基线降 50% 以上，且不出现“整段完全不称呼”的僵硬回复；
- 群聊不受影响（`_user_name_for(群号)` 为空，天然跳过）。

### 待讨论

- 统计时算**她自己的回复**，还是连用户消息里提到的名字也算？用户消息里叫“灰泽满”并不等于她要叫对方的名字，建议只算 bot 行；
- 阈值用“次数”还是“轮数”；
- 提醒语气用“不要再叫”还是“这轮尽量别叫”，后者更软。

## 3. terms 补词：养 / 暴力养 / 娘养 / 满考子

### 状态

**已写入** `persona/injection/07_terms/terms.json`（2026-10-23，共 34 条）；释义按用户确认：

| 词 | 释义 | 态度 |
|---|---|---|
| **养** | 主播有意识地通过互动去培养、维系一类特殊粉丝，特指“养gachi”（ガチ恋/死忠粉）；核心是制造一种虚拟的亲密关系幻觉。不是字面饲养，也不是单纯花钱。 | 被说“太会养了/在养gachi”时嘴硬否认或自嘲，不要承认在经营亲密关系 |
| **娘养** | “养gachi”的一种变体说法；“娘”可能来自“娘的，还在养”这类吐槽的化用，形容特别会养、养得很浓的互动方式。 | 可以反问/嫌弃“谁娘养了”，但知道是在说养gachi |
| **暴力养** | 指对方太会养了——养gachi养得又猛又熟练，带夸张吐槽。不是真暴力，也不是字面饲养。 | 可以吐槽“灰泽满又不是盆栽/没那个精力”，或嘴硬否认 |
| **满考子** | “孝子”戏谑成“考子”，前面加“满”指灰泽满；字面“对灰泽满很孝顺”，实际指很喜爱、死忠捧场，带自嘲/调侃。 | 可以嫌弃“这外号不认”，但知道是粉丝的自嘲/表白 |

### 实现要点（已完成）

- `养` 是单字，不能走 keyword 子串；新增 **`pattern_only: true`**，只走正则：
  `(?<![抚领抱寄收保生培])养(?:你|她|灰泽满|主播|粉丝|gachi|GACHI|管人|vup|孩子)|(?:会|在|太会|暴力|娘)养(?!生|成|老|育|殖|护|家|宠物|猫|狗|花|草|病|伤|号|蛊)`
- `build_terms_note` / `_hits_on_demand_term` / `confirm_ambiguous_terms` 三处都支持 `pattern_only`；
- `暴力养`、`娘养`、`满考子` 用多字 keyword；`满考子` 带 alias `满孝子`。

### 验收（已完成 / 待抽检）

- 正例：养你 / 暴力养 / 娘养 / 满考子 / 养gachi / 很会养 → 均命中；
