## 下一步（按优先级）

### A. 花费：先量清"群聊到底占多少"（用户 2026-10-13 新提）

**背景**：API key 独立出来后，**昨天（10-12）bot 单独花了 ¥8.43**（≈ ¥250/月，比早先估的高）。
用户的假设：**群聊里"把群友说的话都读进去"是大头**。

**已知（从 `chat_log` 粗算，10-13）**：

| | 轮次占比 | 用户消息平均长度 |
|---|---|---|
| 私聊 | 75.1%（8377 条） | 14 字 |
| 群聊 | 24.9%（2771 条） | **38 字** |

而且群聊那条路上**多两次 LLM 调用**（批量归纳 `summarize_batch` + 接话判 `should_reply_in_group`，
私聊单条不归纳），并且用户消息是**整批带昵称拼起来**的（"昵称：内容"×N），还额外注入【群聊现场】。
→ **假设站得住，但 25% 的轮次能不能撑起大头，得实测。**

**实验怎么做**（从省事到准，选哪步等拍）：

1. **先榨干现有插桩**：`log_cache_usage` 已经按 tag 打 `[缓存] <tag>: prompt=N 命中=M`。
   把 bot 输出重定向到文件跑一天，按 tag 聚合 → 各通道的 token 占比。
   ⚠️ 重定向必须 `PYTHONIOENCODING=utf-8`（否则带 ⚠️ 的 print 会抛，见下面 C 节）。
2. **加一格"私聊/群"**：给 tag 拼上 `·群` / `·私`（一行改动），就能**直接把群聊那部分分出来**——
   这是回答问题最直接的一刀。
3. **离线复算**：从 `chat_log` 取真实批次，用 `build_message_list` 复算每类的 prompt 长度，
   不用等真流量。

### C. 名字（私聊里"每句都叫名字"）

现状：**正反馈环已断**（`starts_with_name` + 重生成），存量重复也清了（`memory-dedupe`）。
**还没做的**：
- **降低"可用性"**：把 `preferred_name` 从 `_ALWAYS_ON_FACT_KEYS` 里拿掉 —— 现在是**每轮都注入**，
  等于每轮提醒她"这有个名字可以用"。改成只在**话题相关**时注入，频率天然就下来，**不用写规则**。
  （⚠️ 2026-10-12 实测过一版：移出常驻后她**答不出"你还记得我叫什么吗"**（回"你叫……。"）——
  真要做，得给"被问名字/打招呼"留个后门。）
- 用户 2026-10-11 提的另一个方向：**"你"→名字的确定性替换**。⚠️ 不能字面做：中文里名字是**呼语**
  不是主语（"草草子哥在干嘛"读起来像在说他），而且"你"会撞词（你们/迷你）。要做只能做成
  "**偶尔在分句边界插一个呼语**"，且限频。**未定，先别动**。
- 要做**正向引导**（"只在有情绪/要拉近时才叫"）的话：**别写规则句，改成"用样本教"**。
  理由：上一次的**正向指令**（v1 那句"这个绿冻叫X，聊天时用TA的名字称呼TA"）就是这场
  100% 名字开头的起点——再写一条正向规则，大概率同一个坑（黄金律 1：样本 > 规则）。
  做法：在**情绪类情景的 samples 里**让名字自然出现（比如"对方难过时"那 5 条里放 1-2 条
  以名字起手、其余不带），**同情景内有/无对照** → 模型学到的是"这种时刻**可以**叫名字"，
  而不是"每句都该叫"。
