# 注入链路 —— 她有什么素材、怎么被注进去

> **给使用者看的解剖图**（2026-09-25 实测产出）。回答两个问题：
> ① **素材层**：她有哪些数据、各自干什么用、多少条？
> ② **注入层**：一条消息进来，这些素材是怎么被注给模型的、最后怎么变成那句话发出去？
>
> 所有数字都是**当场跑出来的**，不是估的。带 ⚠️ 的是调研中发现的**问题**（汇总在第七节）。
> 相关文档：`FILE_MAP.md`（谁是什么）、`交接文档.md`（当前状态）、`待办清单.md`（没做的）。

## 一、总图

```
QQ 收到消息
   │
   ├─ __init__.py 抽取（每条都可能改写 user_msg）
   │     引用还原 · 合并转发→摘要 · QQ表情→文字 · 图片（先存，推迟解析）
   │
   ▼
读秒窗口 chat_window.enqueue（私聊按人 / 群聊按群开窗）
   │     每来一条新消息 → 倒计时重置为 random(5,10) 秒
   │
   ▼ 【安静下来了】
_flush 按顺序：
   ① 读图（并发解析本批所有图片）
   ② 组装（群聊加"发送者："前缀 + 记成员昵称）
   ③ 归纳这一批（<2 条不做）
   ④ 群聊接话门 ← 只群聊，判"要不要开口"，判不出来按"接"
   ⑤ handle_chat ↓
   │
   ▼
【检索】六路 → RRF 融合 → top6 → 1200 字预算
   │
   ▼
【注入】build_message_list 组装 18 段 system/user/assistant
   │
   ▼
generate_reply（deepseek-flash, temp 0.85, 150 tokens）
   │
   ▼
clean_reply → 语音优先（成功就结束）→ 否则 split_reply 分段发 → 最后补一张表情包
   │
   ▼
回写：短期/长期/会话/群记忆 + 聊天落盘
```

### 2.4 直播经历（"她经历过什么"）★ 最大的一块

| 文件 | 条数 | 定位 |
|---|---|---|
| `persona/world/statement_final.json` | **322** 条 | **源**：直播转写浓缩成的第三人称陈述（50~120 字） |
| `persona/world/corpus_vectors.json` | 322 条（2048 维） | 向量缓存，运行时只读它 |
| `persona/world/corpus_asks.json` | 181 条 | 「用户可能怎么问」索引——**方案已证伪，运行时无消费点**（见 6.3） |

**来源管线**：直播转写 → `clean_transcript` → `generate_statements`（模型浓缩）→ **人工合并** → `generate_vectors` → 向量库。

⚠️ **不可复现**：只有 111/322 条能追溯到 `generate_statements`；「合并 → statement_final」这一步**没有脚本、是手工做的**，源无法重放。
⚠️ **长度两极，会被截断**：75 条 >120 字、**13 条 >300 字**（最长 610 字），而注入端单条上限 `MAX_RETRIEVAL_ITEM_CHARS = 300` → 那 13 条**每次注入都被砍掉后半段**。
⚠️ **向量库里没有 id/来源/时间**（只有 `text` + `vector`），不可追溯性由此固化。

## 三、注入层：一条消息进来发生什么

### 3.1 前置：收到 → 决定要回

**入口抽取**（`__init__.py`，每条都可能改写正文）：

| 抽取 | 变成什么 |
|---|---|
| 引用消息 | `[引用{谁}说的：「…」]` 放在**正文最前**，只留 80 字，who 分三档（灰泽满自己/对方自己/另一个绿冻昵称） |
| 合并转发 | 取回后**只注入一句话摘要**（几十条原文会挤爆上下文） |
| QQ 内置表情 | 取 `faceText` 变成文字（拿不到时查 248 条的对照表兜底） |
| 图片 | 只取第一张的 url/file 存着，**推迟到 flush 才解析** |

**读秒窗口**（`chat_window.py`）：

- **私聊按人开窗，群聊按群开窗**（整群共用一个缓冲）——这是"bot 参与整场群聊"而不是一问一答的原因。
- 每来一条新消息：**倒计时清零重排**，静默 `random(5, 10)` 秒才处理。攒批上限 30 条。
- **插话取消**：她正在分段发消息时用户又说话了 → 未发出的分段**直接不发**（已发出的收不回）。语音路径用 `asyncio.shield` 豁免这条，一旦开始合成必做到底。

**`_flush` 的 14 步**：读图 → 组装（群聊加"发送者："前缀）→ 归纳本批 → 群聊接话门 → `handle_chat` → `clean_reply` → 聊天落盘 → 语音优先 → 文字分段 → 表情包。

**群聊接话门**（`group_gate.py`，**私聊不走**）：判据是用户标定的四条——被点名必接 / 有情绪可以接 / 有人分享经历偶尔接 / 纯事务附和收尾不接。**失败按"接"放行**（判成哑巴比多说难发现得多）。`GROUP_GATE=0` 可关。

### 3.2 检索：六路 → RRF → 预算

**六路**（`retrieval.py`）。query 只调 **1 次** embedding，六路共用：

| 路 | 怎么判 | 阈值 | 条数 | 走 RRF？ |
|---|---|---|---|---|
| **corpus** 直播经历 | 关键词门直通 **＋** 门没放行的取 top-6 交 LLM 判 | 语义 0.48 / 词重叠 0.12 / 强词 0.8 | top3 | ✅ w=1.0 |
| **voice_sample** 风格样本 | 纯余弦 | **0.66** | top3 | ✅ w=1.0（有 short 档时 +0.3） |
| **behavior** 行为 | **LLM 分类**（判别词退为兜底） | — | 1 | ✅ **w=1.5** |
| **phrase** 措辞 | **LLM 分类**（同一个 L3 调用给组 id） | — | 2 组 | ✅ w=1.2 |
| **preference** 偏好 | **keywords 子串命中**，命中才带 | — | top2 | ❌ 不占预算 |
| **core_story** 核心记忆 | 纯余弦，**命中才带** | 0.42 | top2 | ❌ 不占预算 |

### 判据怎么选（2026-09-26 定，别再搞混）

**同一个"检索"外观下其实是三种任务，工具完全不同：**

| 任务 | 特征 | 该用什么 | 谁在用 |
|---|---|---|---|
| **归类** | 类别少（十来条），要判"这句话属于哪类" | LLM 分类，或判别词 | behavior、phrase |
| **关键词命中** | 类别名用户能直接说出来（"吃"/"猫"/"宝可梦"） | 子串命中（零成本、可人工审、能写测试） | terms、legendary、preference |
| **检索** | 要说从哪里**挑**，说法不可枚举 | 向量召回 + LLM 判 | corpus、voice_sample、core_story |

⚠️ **phrase 和 preference 原来都坐错了位子**（它们分别该是"归类"和"关键词"，却都用向量），
实测两路的噪声地板都**压在正例上**：phrase 地板 0.575 / 正例 0.573；preference 地板 0.565 插在
正例 0.501/0.552/0.590 **正中间**。改判据后 smoke 数据：**phrase 100% 开火 → 20%，preference 19% → 5%**。

**RRF 融合**（`rrf_fuse`）：`分数 = 权重 / (60 + 本路内排名)`。
⚠️ 关键细节：**排名是"路内排名"**，所以弱路里的第 1 名（如 phrase 的 0.0197）能压过强路里的第 3 名。`SOURCE_WEIGHTS` 就是用来调这个的。

**实测 trace**（「说好的八点直播呢？都八点四十了」）：

```
corpus       4条  168@0.590 | 113@0.522 | 44@0.517 | 171@0.542(LLM判捞的)
voice_sample 3条  sample_late_8pm@0.767 | miss_6@0.728 | miss_7@0.728
behavior     1条  失约被催时认栽滑跪@1.000
phrase       2条  busy_excuse@0.706 | greeting@0.596
→ RRF 后 top6 → 1200 字预算内实际 6 条
   rank1 fusion=0.0246 behavior(333字)   ← w=1.5 的路内第 1
   rank1 fusion=0.0213 voice_sample(31字)
   rank2 fusion=0.0210 voice_sample(21字)
   rank3 fusion=0.0206 voice_sample(27字)
   rank1 fusion=0.0197 phrase(11字)
   rank2 fusion=0.0194 phrase(20字)
另：偏好 1 条 / 核心记忆 1 条（命中才带，不占预算）
```

对照「今天在干嘛呀」：corpus/sample/behavior **全空**，只有 phrase 2 条 → 融合后 2 条。**日常闲聊注入得很少**，这是正常的。

**预算**：`RETRIEVAL_TOPK=6` 条上限 → `RETRIEVAL_BUDGET_CHARS=1200` 字贪心截断 → 单条 `MAX_RETRIEVAL_ITEM_CHARS=300`。

### 3.4 生成与后处理

**生成参数**：`deepseek-flash`，`temperature=0.85`（低温她会走 RP 括号模板）、`frequency_penalty=0.3`、`max_tokens=150`、**显式关闭思考模式**。

失败兜底：`哎呀，hzm脑子卡了一下……` / `……（沉默，可能是信号不好）`——**这两个文案永不进记忆**（曾污染过历史）。

**`clean_reply` 的确定性处理**（`reply_style.py`，六组规则）：

1. **换行归一**：行内空白 + 连续换行归一；断行跟在标点后 → 直接接上；跟在实词后 → 补逗号（两行焊死会读成 run-on）。她的输出永远该是"一条消息、一口气"。
2. **剥掉开头的连续括号前缀**（`（咽口水）你看…`）——剥光了就回退到归一后的原文，别返回空。
3. **整条至多 1 个括号**，多余的删。
4. **省略号纪律**（4 条子规则）：连续省略号归一成 `……`；剥掉开头的；开头"词+省略号"的犹豫 → 改逗号；**整条至多 2 个**。
5. **结巴消融**：`那、那` → `那那`。
6. **自指"她/他"兜底**：只有文本含"灰泽满/hzm"、且**不含任何别人名**（白名单来自 terms 的人物/关系词 + 硬编码专属人物）时，才删掉指代自己的"她/他"。**宁可不替换（留个小瑕疵），也不误替换（把别人的行为安到她头上）**。

清洗后为空 → `……`；反复读入是幂等的。

**分段发送**：`split_reply` 按句切 → 每段至多 1 个逗号 → 纯括号段并上一段 → 短段（<8 字）并入 → 最多 4 段（第 4 段起用逗号接成一条）。
段间停顿 = `clamp(1500ms + 100ms×字数, 1800, 5000) × (1±15%)`，**实际约 1.8~5 秒**。

**语音优先**：满足条件就发语音，**成功就不发文字**（互斥）。条件：不含内心戏括号（小声/心虚/捂脸…）、不含数字和链接、朗读文本长度 30~120 字（或 ≤12 字的真寒暄句）。
**失败一律退回文字**（语音挂了照样收得到回复）。

**表情包**：文字发完之后**额外补发一张**（语音路径不发）。LLM 判"有没有十分对应的"，**判不出来不发**（发错比不发难看）。冷却 3 轮。

**三个判定的兜底方向刻意相反**：

| 判定 | 失败时 | 为什么 |
|---|---|---|
| 群聊接话门 | **接**（放行） | 判成哑巴是难发现的故障 |
| 表情包 | **不发** | 发错只是难看 |
| corpus 语义判 | **不带经历** | 想起错的是**主动伤害**（她会理直气壮说没发生过的事） |

### 3.5 回写（记忆）

- **短期**：存的是 `clean_reply(reply)` 而不是原始输出——否则她带换行/多括号的原始输出会当 few-shot 被喂回自己，形成自我强化回路。
- **长期**：异步提取（只抽事实，与说话风格无关，所以这里用未清洗的 reply）。
- **兜底文案整轮不记**（用户那句也不留）。
- **聊天落盘**：`data/chat_log/`，记清洗后的回复，**刻意放在语音 return 之前**（否则语音回复全漏记）。

## 四、实测数字

### 4.1 一轮注入多大？（真实跑 handle_chat，把 messages 截下来量的）

| 场景 | message 条数 | 总字符 | base system 占比 |

## 六、几个"为什么是这样"（踩过的坑，别走回头路）

**6.1 为什么周表 > 记忆**：记忆里带"明天/下周"的话，是过去某场直播**当时的**说法，早过期了。周表是 weekday 制，永远对。

**6.2 为什么提示词里写不出台词**：`behaviors.response` 里曾写"用'呃…'起头"，实测 **10/10 说"呃"、其中 8 条逐字相同**；改掉后 0/10。而 86 条真实样本里 **0 条**以"呃"开头——那个"呃"完全来自提示词，不是她。
→ **判据：注入的措辞要描述到"没有可以被直接搬走的词"的粒度为止。**
→ **给句会被整句抄，给词只能织进自己的句子**——所以"让她说出某个内容"的正确位置是 `phrases.json`。

**6.3 为什么 corpus 不再用"用户可能怎么问"当索引**：
`corpus_asks.json`（485 条）把正例从 0.44 拉到 **0.88**，**但噪声地板同步抬到 0.822**——「明天几点开会」vs 库里「明天几点下课」在语义、共享 bigram、IDF 加权三种算法下**全都分不开**（比部分正例还高）。
**差别不在文本里，在"她到底有没有这段经历"这个事实** → 只能 LLM 判。
（顺带证伪的还有"把 asks 拼进陈述一起编码"：稀释后排名几乎不动。）

**6.4 为什么"一致性规则"被删了**：旧文案写「借口要与之前保持一致」——**那是直接教它复读**。实测把第一次的随机选择（"威严"、"搬家"）锁成了永久设定，用了一周。现在只管**事实**别打架，明确不管**说法和态度**。

**6.5 为什么记忆里存的是清洗后的回复**：见 3.5——不清洗会让后处理的坏习惯被 few-shot 自我强化。
