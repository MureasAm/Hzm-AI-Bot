## 0. 总览：一条消息的旅程

### 0.1 一句话

```
用户说一句话
→ 攒批（读秒窗口等 5~10 秒）
→ 判别（这段文本落在哪个情境 / 该不该接话）
→ 检索（两路 RRF + 两路直达，从素材里挑相关的）
→ 组装（按固定顺序拼成 17 个逻辑段，最后一条是用户原话）
→ 生成（DeepSeek）
→ 后处理（clean_reply 确定性清洗 → 语音优先 → 分段发送 → 补表情包）
→ 回写（短期 / 会话 / 长期 / 群 四层记忆）
```

**模型看到的是 messages，不是文件。** 文件是维护单位，messages 才是模型实际接收的内容。
模型不会看到 JSON，也不会看到目录；它只会看到一段段 system / user 文本。

### 0.2 全链路（带代码入口）

```
NapCat → __init__._handle_chat                      （src/plugins/chatbot/__init__.py）
   ├─ 抽文字 / @ / 引用 / 转发 / 图片 / QQ 表情
   │   · 引用回复：把"引用了哪条"放到消息最前（引用的那条本身是转发卡片时，单独取摘要）
   │   · 合并转发：取回聊天记录 → 摘要 → 只注摘要（转发动辄几千字，原文不进上下文）
   │   · @ 她：在文本前插 AT_SELF_MARK（"@她 + 正文"里正文没有名字，接话门命中不了）
   │   · QQ 内置表情：含义转成 [表情：xx] 并入消息
   │   · 只含"没解析的段"的消息：注入占位提示（否则会静默消失，连日志都没有）
   └─ chat_window.enqueue(target_id, …)            ← target_id：私聊=user_id，群聊=group_id
         │
         ├─ _process：睡 5~10 秒（随机读秒窗口），期间被插话就取消重来
         └─ _flush                                  （src/plugins/chatbot/chat_window.py）
               ├─ 读图（vision，本批所有图片一次性解析；失败给兜底描述保证可回）
               ├─ 群聊：每条加发送者昵称（并存进群成员表）
               ├─ summarize_batch（≥2 条才归纳，单条零额外延迟）
               ├─ 群聊：写群近况（带 300s 冷却，防碎碎念刷爆）
               ├─ 群聊：should_reply_in_group（接话门）——不接则只记不发，结束
               └─ core.handle_chat                  （src/plugins/chatbot/core.py）
                     ├─ 会话探测 probe_session（同步，对话前跑，扩充短 query）
                     ├─ 梗库硬匹配 legendary（命中 + LLM 确认 → 直接当回复返回）
                     ├─ gather_retrieval（见第 2 节）
                     │     ├─ classify_l3        → 行为 + 连续索要       【1 次 LLM】
                     │     ├─ embed_query        → 向量                 【1 次 embedding】
                     │     ├─ corpus 候选召回 → judge_corpus 判         【1 次 LLM】
                     │     ├─ terms / legendary / preference / core_story（纯本地）
                     │     └─ 记忆两路（长期卡 / 会话）
                     ├─ build_message_list      → 17 段 messages        （见第 3、4 节）
                     └─ generate_reply          → 模型生成              【1 次 LLM】
               → clean_reply（确定性兜底）
               → 语音优先：should_voice → send_voice，成功就不发文字（之后仍补表情包）
               → split_reply（拆句 + 打字延迟） + _maybe_send_sticker
```

### 0.3 每一轮的固定成本

| 调用 | 数量 | 触发条件 |
|---|---|---|
| LLM（判行为/连续索要，`classify_l3`） | 1 | 是"用户说的话"（私聊、群聊都算；主动发言不算） |
| embedding（`embed_query`） | 1 | 同上 |
| LLM（判语料，`judge_corpus`） | 1 | 有候选 |
| LLM（会话探测 `probe_session`） | 1 | 每轮，对话前 |
| LLM（生成回复 `generate_reply`） | 1 | 总是 |
| 视觉（`vision`） | 0~N | 本批有图片 |
| LLM（表情包 `pick_sticker`） | 0 或 1 | 冷却到 + 内容十分对应 |
| LLM（长期记忆提取 `update_memory_task`） | 1（异步） | 消息 ≥4 字、非纯表情、非群聊 |
| LLM（群聊接话门 `should_reply_in_group`） | 0 或 1 | 群聊且非点名（点名确定性放行，不调 LLM） |

> 定性：**每轮 2~5 次 LLM + 1 次 embedding**（判行为、判语料是检索层的两次；生成一次；会话探测一次；群聊多一次接话门）。记忆提取是异步后台，不阻塞回复。

### 0.4 读秒窗口（攒批）——"发生了什么"这一步

**`chat_window` 的三个职责**（模块头写明）：

| 阶段 | 机制 |
|---|---|
| **采集** | `enqueue()` 把每条消息以及图片塞进该会话的缓冲，**重置去抖定时器** |
| **会话** | `enqueue` 重置定时器；用户停手超过随机读秒窗口（`READ_WINDOW_MIN_SECONDS=5.0` ~ `READ_WINDOW_MAX_SECONDS=10.0`）才触发一次回复 |
| **回复** | `_flush` 在回复前统一"读图 + 归纳"（作为读整批的一部分），再交给 `handle_chat` |

- **按 target_id 开窗口**：私聊按 user_id、群聊按 group_id（群成员发言攒同一个窗口 → 群=回整场群聊）。
- **插话取消**：`enqueue` 时若有在跑的任务先 `cancel()`，再起新任务。窗口里塞超过 30 条会只留最近 30 条。
- **generation 代际**：每次 enqueue 自增。回复到一半若已被新消息取代（`win.generation != my_gen`），语音合成会被跳过（合成了也送不出去）。
- **语音合成用 `asyncio.shield`**：一旦开始就让它做完。不 shield 的话，用户插话 → `cancel()` 打断 `sent_voice` → **wav 已生成、消息没发出去**，文字兜底也不走（`CancelledError` 是 BaseException，`except Exception` 抓不到）——她那边什么都收不到。

### 0.5 生成后处理——"模型已经生成的那句话"

| 步骤 | 函数 / 文件 | 做什么 |
|---|---|---|
| 清洗 | `reply_style.clean_reply` | 换行归一（她的输出永远"一条消息一口气"）、去开头括号前缀、整条至多 1 个括号、省略号归一且至多 2 个、"那、那"→"那那"、第三人称自指兜底 |
| 防复读 | `reply_style.is_echo_reply`（窗口 8） | 与最近自己说过的话高度重复 → 追加一条 nudge 强制"换动作"重生成（最多 3 次） |
| 语音优先 | `voice.should_voice` / `send_voice` | 成句（剥括号后 ≥`VOICE_MIN_LEN=30` 字）或无内心戏括号/链接/数字 → 朗读；成功就不发文字 |
| 分段发送 | `reply_style.split_reply` / `split_delay` | 长回复拆成几句分批发（`SPLIT_MAX_PARTS=4`），句间延迟按字数模拟打字（1.8~5s） |
| 表情包 | `stickers.pick_sticker`（冷却 `STICKER_COOLDOWN_TURNS=3`） | 文字/语音发完后，若有"十分对应"的表情补一张 |

**语音的几条铁则**（`should_voice`）：
- 长度/寒暄判断用**实际会读出来的文本**（剥括号后）——避免"原文带括号尾巴够长、读出来只剩短句"的误触发。
- **内容铁则**（最高优先，看原文）：内心戏括号、数字/链接 → 转文字（读出来没意义/发不出去）。
- `force=True`（用户点名要语音，`voice_requested` 命中"语音/录音/发个声音"）→ 放宽**长度**闸门，短句也读；但内容铁则仍最高优先。
- 短寒暄（晚安/辛苦啦…，`_GREETING_PHRASES`）可突破长度下限，但只救"真·短应酬句"（≤12 字）。

## 1. 判别层 — 四种判定方式

一个素材文件"什么时候被注进去"，靠的是下面四种机制之一。**改素材前先确认它属于哪种——改错了地方不会生效。**

### 1.1 四种判定方式

| 判定方式 | 机制 | 代价 | 特点 |
|---|---|---|---|
| **① 常驻**（无条件） | 每轮都注 | 骨架占预算大头 | 与内容无关，永远在 |
| **② 关键词 / 子串 / 正则** | 用户消息里出现关键词/别名/正则就注 | 免费（本地纯函数） | 零成本、可解释、可人工审、能写测试 |
| **③ 向量相似度** | 余弦 ≥ 阈值 | 一次 embedding | "说法不可枚举、要从 N 条里挑" |
| **④ LLM 判断** | 叫一次 LLM 读语义 | 一次 LLM 调用 | 判"是不是一回事 / 该怎么归类" |

> 一个贯穿全仓的取向：**少用 LLM，能确定性判的就确定性判**。LLM 只放在"确定性判据分不开"的地方（归类、判"说的是谁"、"十分对应才发"这类）。

### 1.2 谁用哪种

| 文件 / 来源 | 判定方式 | 走 RRF？ | 备注 |
|---|---|---|---|
| `core/system_prompt.txt` | **① 常驻** | — | 骨架 3413 字，每轮第 1 段 |
| `world/schedule.json` | **① 常驻**（只注 `weekly`） | — | 地面真值，回答"明天/几点播" |
| 时间 / 农历 / 天气 / 直播状态 | **① 常驻** | — | `context_probe.get_now_context` |
| `world/terms.json` | **② 关键词/别名/正则** + `priority=always` 的常驻 | — | `usage` 只在命中或概念词出现时才注 |
| `world/preferences.json` | **② 关键词/正则** | 否（直达） | **不走向量**（2026-09-26 改判据） |
| `world/legendary.json` | **② 关键词/正则** + LLM 语境确认 | — | 命中直接当回复返回，**不进检索、不进 messages** |
| `behavior/behavior_keywords.json` | **② 关键词** | — | L3 判不出时的兜底词表 |
| `world/corpus_keywords.json` | **② 关键词**（钩子） | — | 只负责"把条目递进候选池" |
| `world/statement_final.json`（→ `corpus_vectors.json`） | **③ 向量初筛 + ④ LLM 再审** | 是 | 两道路径见 2.1 |
| `world/core_stories.json`（→ `core_story_vectors.json`） | **③ 向量** | 否（直达） | 低阈值高浮现 |
| `behavior/behaviors.json` | **④ LLM 分类**（`classify_l3`） | 是 | **不走向量**；判别词兜底 |
| 连续索要计数 | **④ LLM**（同上一次调用里的 `same_request`） | — | 只给事实"第几轮在要什么" |
| `media/stickers.json` | **④ LLM** | — | 发/不发/发哪张 |
| 群聊接话门 | **④ LLM**（+ 点名确定性放行） | — | 只在群聊用 |
| 记忆（长期/会话/本场/群） | 按会话状态 | — | 见第 5 节 |

### 1.3 为什么这么分（判据按任务选）

三种任务，三种工具——这是本仓最稳的一条设计律：

| 任务 | 特征 | 该用什么 | 现在谁在用 |
|---|---|---|---|
| **归类** | 类别少（十来条），判"这句话属于哪类" | LLM 分类（判别词只作兜底） | `behavior` |
| **关键词命中** | 类别名用户能直接说出口 | 子串命中 | `terms` / `legendary` / `preference` / `corpus` 钩子 |
| **检索** | 要从 N 条里**挑**，说法不可枚举 | 向量召回 + LLM 判 | `corpus` / `core_story` |

**两个反面教材（2026-09-26 已修）**：`phrases`（措辞）和 `preference`（偏好）**原本都坐向量检索的位子**，但它们分别是"归类"和"关键词"任务。症状是量出来的——**噪声地板压在正例上**：

| 路 | 噪声地板 | 真信号（正例） | 结论 |
|---|---|---|---|
| phrase | **0.575** | **0.573** | 完全重叠；中位数 0.461 都过阈值 0.40 ⇒ **等于没有阈值** |
| preference | **0.565** | 0.501 / 0.552 / 0.590 | 地板**插在正例正中间**；提到 0.62 则三个正例全被杀 |

**根因（决定性）**：措辞组的 `trigger` 是 **6~13 字的类别标签**（「被夸奖、被称赞时」）——**这是标签，不是句子**。拿"用户说的话"和"一个类别标签"算余弦，是拿检索工具干分类的活。对照：`behaviors` 的 trigger 长得一模一样（「收到正面评价或夸奖时」），但它**从不拿 trigger 去匹配**（靠 LLM 判意图 + 判别词兜底）——**同一个形状的问题，一个是通的，一个是坏的，差别只在工具**。

修完的结果：

| | 改前 | 改后 | 怎么改的 |
|---|---|---|---|
| phrase 开火率 | **100%**（每轮都塞，假信号） | **20%** | 组 id 由 L3 分类给出 |
| preference 开火率 | 19% | **5%** | 每条挂 `keywords`，子串命中 |
| 判据有效性 | 100% 是假信号 | 逐条看过，**无误报** | — |

### 1.4 ⚠️ 失败往哪边倒（**最容易踩的坑**）

**同类模块，判据失败时的兜底方向可以完全相反——这不是不一致，是按后果选的。** 改这些模块前先想清楚"失败时应该往哪倒"。

| 模块 | 失败时 | 方向 | 为什么 |
|---|---|---|---|
| `corpus_judge`（判语料） | 判不出 → **返回 []（宁可漏）** | **宁可漏不可错** | 注入错的经历是**主动伤害**——她会理直气壮说一件没发生过的事（"搬家"那个坑就这么来的）。漏掉只是"没加分"。 |
| `group_gate`（群聊接话） | 判不出 → **返回 True（宁可放行）** | **宁滥勿缺** | "偶尔安静"是风格，"该说时不说"是故障——后者更难发现也更伤。一次上游抖动不该把她变成哑巴。 |
| `stickers`（表情包） | 判不出 → **返回 None（不发）** | **宁可少发不可发错** | 发错表情比不发难看得多。 |
| `legendary_confirmed`（梗确认） | 失败 → **放行** | 放行 | 关键词命中是低频事件，确认失败不阻塞。 |
| `confirm_ambiguous_terms`（术语语境确认） | 失败 → **放行（空集）** | 放行 | 不丢注入——和 legendary_confirmed 同策略。 |
| `classify_l3`（行为分类） | 失败 → **空（不触发）** | 不触发 | "拿不准一律不放（宁可不触发，不误触发）"。 |
| `gather_retrieval`（整个检索层） | 异常 → **按"没检索到"继续** | 继续 | 检索层炸了不能让她变哑巴（2026-09-27 曾因 embedding key 过期导致整条回复任务死掉）。 |
| `generate_reply`（生成） | 异常 → **兜底文案** | 兜底 | 且兜底文案**绝不写进记忆**（见 `is_fallback_reply`）。 |
| `summarize_batch` / `summarize_forward` | 失败 → **空串** | 降级 | 调用方忽略，原文照旧。 |

> 记住这条分工：**corpus 失败往"漏"倒、group_gate 失败往"放行"倒、stickers 失败往"不发"倒。**
> 三者方向不同是**设计**，不是缺陷——改的时候别一刀切。

### 1.5 legendary 硬路由（梗库）

**不是检索，是"命中就直接当回复返回"，压根不进 messages。**

- 数据：`persona/world/legendary.json`（现 **9 组应答 / 8 组确认**）。
- 双路由：**关键词/正则粗筛 + LLM 语境确认兜底**。
  - `legendary_hit(trigger, msg)`：**配了 `pattern` 就以 pattern 为准；没配才回落到子串**。
    > 为什么不是"子串或正则"：那样 pattern 只能**放宽**（加更多说法），没法**收紧**——裸触发词（如「没感觉」）会先被子串命中（"这歌我没感觉"）。改成"pattern 优先"后，一个词既能放宽也能收窄，由数据说了算。
  - `legendary_confirmed(user_msg, prompt_template, history)`：再叫一次便宜 LLM 判"是不是真是目标梗的语境"（防误触发）。**失败默认放行。**
- 命中后：`random.choice(replies)` 直接返回，**并记入短期 + 异步长期记忆**（避免后续对话"失忆"）。

**入口审计（2026-09-27）**——"让 LLM 写'用户会怎么问这件事'，再拿它跑真实匹配函数"：

| 路 | 能勾出来 | 诊断 |
|---|---|---|
| `core_story` | **5/5 = 100%** | ✅ 语义路，问法都能召回 |
| `terms` | 18/26 = 69% | 部分是真缺口、部分是审计盲点、部分是设计如此 |
| `legendary` | **5/20 = 25%** | ❌ 最严重的病 |

**legendary 的病根**：5 条触发词是同一个梗（问年龄 → 答"永远16岁"），回答几乎一样——**违反「单一真值」**；且用户实际说法（"你到底几岁啊"）一条都不命中（子串匹配假设用户会说精确词）。
**已修（入口覆盖 25% → 89%）**：① 合并重复条目（5 条"问年龄"→1 条等，**16 组 → 9 组**）；② 给窄触发词配 pattern；③ 给放宽的补 `confirms`（**3 组 → 8 组**）——粗筛放宽负责不漏，LLM 确认负责不错。
> ⚠️ 但有一类判断正则做不到：`没感觉` 到底指不指感情**要看上下文** → 撤掉 pattern，回到子串触发 + 靠 confirms 结合最近对话判断。**该 LLM 判的就别硬用正则。**

### 1.6 terms 名词库（lorebook）

`build_terms_note(user_msg, denied_terms)` → 注入【灰泽满的世界】。**客观打底 + 带灰泽满态度**：让模型既懂词义又有正确的相处态度。

**命中检查（`terms.json` 现 27 条，always 1 条）：**

| 字段 | 含义 | 生效条件 |
|---|---|---|
| `priority=always` | 核心词 | 每轮注入 |
| `keyword` / `aliases` | 词/别名 | 子串命中 |
| `pattern` | 正则 | 正则命中（用于子串做不到的场景） |
| `usage` | "主动用词规则"（表达这个概念时用这个词） | **关键词命中 或 概念词出现**时才注（不常驻，避免"每条都蹦黑话"） |
| `usage_triggers` | 概念触发词 | 消息出现这些词（关键词没命中）时**只注入 usage** |

> `pattern` 的用途举例：`区` 单字会撞"小区/地区"，用 `满区|(这么|太|好|很|真…)\s*区` 只命中"满区"或形容词用法。
> `usage` 的双向设计：让模型讨论这个概念时**主动用黑话称呼**，而不是只会听懂。

**`confirm: true` 的词条**：命中后走一次 `confirm_ambiguous_terms`（LLM 语境确认，词→意思的准确性守卫）——防 pattern/短词命中误触（如'满区'命中'怎么这么区'，可能是普通形容词用法而非黑话）。返回应剔除的 keyword 集合，交给 `build_terms_note` 跳过。**失败/无客户端默认放行（不丢注入）。**
> ⚠️ `confirm_ambiguous_terms` **函数是存在的**（旧 `注入链路.md` 说它不存在——那是错的）。

### 1.7 群聊接话门（`group_gate.py`）

**为什么需要**：群聊里"有话就接"不像群友——真人只挑着接。**判定粒度是"批"，不是单条**：读秒窗口攒出来的那批就是她的一个观察单位。（逐条判会"蹭余温"——情绪一出现，后面每条都靠它的余温被判成该接。）

**判据（五档）：**

| 档 | 情况 | 结果 |
|---|---|---|
| ① 点名 | 有人明确问她 / 点她名 / 引用她的话 | **必接** |
| ② 情绪 | 本批有情绪表达（"我服了""好惨"，纯情绪也算） | 可以接 |
| ③ 经历 | 有人分享自己的经历或状态 | 偶尔接 |
| ④ 事件 | 纯事件（陈述一件跟她无关的事） | **按概率接**（`GROUP_EVENT_REPLY_PROB=0.3`） |
| ⑤ 事务 | 纯事务、纯附和、收尾语 | 不接 |

- **点名是确定性信号，不调 LLM**：`_addressed_to_her` 认 `AT_SELF_MARK`（@ 段在纯文本里看不见，由 `__init__._extract_at_self` 在消息前插）+ 名字表（`_SELF_NAMES`）兜底。
  > 踩坑（2026-09-25）：群里 @ 了她、还写了名字，却被门判成"不用接"。能确定的事不该调 LLM——多一次调用就多一次判错的机会。
- **纯事件档**：LLM 说"不接"时**改成掷骰子**（0.3）。⚠️ 只**加**不**减**：LLM 明确说"接"就照接——"该说时不说"是这个门最怕的故障。
- **失败一律返回 True（宁滥勿缺）**——见 1.4。
- `GROUP_GATE=0` 可整体关掉。

### 1.8 表情包（`stickers.py`）

**为什么用 LLM 判、不用向量阈值**：要的是"**十分**对应"。阈值调不准——群聊接话门那边已吃过教训（同一份数据、判据稍动就从 0% 跳到 74%）。三十来张的清单塞进提示词很便宜，让模型直接判"有没有十分对应的、没有就 null"更稳。

- 数据：`persona/media/stickers.json`（现 **31 张**）；文件名是一串哈希，模型不知道画的是什么、什么时候该发 → `scripts/label_stickers.py` 离线用视觉模型问出 `desc/tags/use_when`。
- **失败一律返回 None（不发）**——见 1.4。
- **去重按类别不按张**（`avoid_groups`）：同一类里可能有好几张（委屈 3 张、无语无奈 4 张），按单张挡不住"换一张还是同一个味道"。最近发过的类别记 `STICKER_RECENT_KEEP=3` 个。
  > ⚠️ 别按"张"理解这个数字：库里有 18 类，记 8 类等于把近一半锁死，所以从 8 降到 3。
- 冷却：距上次发过表情包至少隔 `STICKER_COOLDOWN_TURNS=3` 轮才再考虑。**这只是冷却，不是频率**——真正决定发不发的是"表情与这句话是否十分对应"。
- **提示词约束不可靠**："别再选最近发过的"在提示词里说了，但**模型不一定听（实测 2 次里 1 次照选）**——所以代码里再用一道拦：宁可这轮不发，也不连着甩同一类的。

## 2. 检索层 — 两路 RRF + 两路直达

### 2.0 全景

```
embed_query（1 次 embedding，全链路共用）
  │
  ├─ corpus   ── 向量召回候选 → 关键词门/钩子补位 → LLM 判 → 保留 ≤2 条 ┐
  ├─ behavior ── L3 LLM 分类 + 判别词兜底 → 按名字查表 1 条 ───────────┤ 走 RRF
  │                                                                    │（fuse_and_truncate）
  │                                    RRF 融合 → top 6 → 1200 字预算 →┘
  │
  ├─ preference ── 关键词/正则子串命中才带（≤2 条）  ┐ 命中直达
  └─ core_story ── 向量 ≥0.42 命中才带（≤2 条）      ┘ 不占检索预算
```

> ⚠️ **代码里只有 corpus + behavior 两路进 RRF。** preference / core_story 是"命中才带"、**不进 RRF、不占 top-6 名额和字符预算**——它们是身份事实层，避免与风格素材抢预算。
> （`retrieval.py` 模块头注释里还留着"两路 RRF + 两路直达"的说明；`voice_sample` / `phrase` 两路已于 2026-10-04 随对应文件删除。）

### 2.1 corpus（直播记忆 / 背景记忆）

**文件链**：源 `persona/world/statement_final.json` → 运行时向量库 `persona/world/corpus_vectors.json`（现 **421 条**）。

**为什么加一道 LLM 判**：用户是**口语问句**（"你多高啊"），库里是**第三人称陈述**（"灰泽满被问到身高，说1米6"）——两种形态不同构，余弦只有 0.443，低于噪声地板 0.474 → 被当"不相关"扔掉 → **她明明有的经历想不起来，只能现编**。

**候选召回 `retrieve_corpus_candidates(query, query_vector, top_n=CORPUS_CANDIDATE_N)`**——三部分拼起来（顺序 = 相关性顺序）：

| 部分 | 来源 | 条数上限 |
|---|---|---|
| ① 语义 top-N | 按余弦降序 | `CORPUS_CANDIDATE_N = 6` |
| ② 钩子命中 | `corpus_keywords.json` 里该条的词出现在 query 里 | 与③合计封顶 `CORPUS_LEXICAL_EXTRA_N = 6` |
| ③ 区分性词重叠 ≥ FLOOR | `_corpus_keyword_overlap ≥ CORPUS_KEYWORD_FLOOR(0.12)` | 同上 |

> ① **为什么敢不过阈值**：实测正例对正确那条的**排名**是对的（"你多高啊"→ 身高那条排第 1），只是分数（0.443）低于噪声地板——**排序有用、阈值没用**。把打分交给排序，把"相关不相关"交给 LLM 判。
> ②③ **只看词面、不看语义分**：要救的正是"语义分低但用户确实提到了"的那批（如 co9 的目标条 `sim` 不到 0.48、`ov` 只有 0.143）。若沿用 `_corpus_gate_pass`（还要求 sim≥0.48），**它正好被挡在外面**。
> **封顶是必要的**：`ov≥0.12` 很松（实测有的 query 能过 29 条），不封会把判定池灌爆——见 2.5 的"候选给多了反而更差"。

**钩子的由来**：实测 400+ 条里有一大批**没有任何召回入口**——用户不可能说出一句话恰好把它们勾出来，于是永远不会被注入。语义检索解决不了这个：那是"像不像"，这里缺的是"**提没提到**"。

**关键词门 `_corpus_gate_pass`**：区分性词重叠占比（去掉领域停用字/名字后的 bigram 重叠）`ov ≥ CORPUS_STRONG_KEYWORD(0.8)` → 放行；或 `sim ≥ RAG_THRESHOLD(0.48) 且 ov ≥ CORPUS_KEYWORD_FLOOR(0.12)` → 放行。
- 领域停用字：`灰泽满/绿冻/直播/你我他的…`；先整词剔除名字/实体（"灰泽"残留在每句陈述里会污染重叠度）再算 bigram。
> ⚠️ **门现在只决定"值不值得让 LLM 看一眼"，不再直通注入。** 2026-09-29 取消了"门放行直通"——实测**基于词重叠的尺子分不开"说的是谁"**：

| | ov（区分性 bigram 重叠度） |
|---|---|
| 误报 n7「宝宝我明天要早起我先去睡了」（用户在说**自己**）→ #271 | **0.40** |
| 真阳性 co9「你不是以前有喜欢的男学霸吗」（在问**她**）→ #42 | **0.143** |

> **误报的重叠度反而更高。** 提到 0.5 确实挡住了 n7，代价是 co9/co10 一起被打回红。换一把尺子（**bigram 文档频率**）也一样，方向同样相反。根因：两条的唯一差别是「**说的是谁**」——那是 LLM 判的事。→ 杠杆只剩一个：**别让它绕过判定**。
> ⚠️ 配套改动：门放行的条目现在必须**进候选池**（原来不进——它就靠"直通"这一条路）。不加这一步，"取消直通"会退化成**丢召回**。
> ⚠️ 副产物：`CORPUS_STRONG_KEYWORD`（0.8 直通）在 50 条评测上**一次都没触发**（最高的 co1 目标条才 0.833）。它现在是纯冗余，别指望它在挡噪声上出过力。

**LLM 判定 `judge_corpus(deepseek_client, query, candidates)`**（`corpus_judge.py`）：
- **一次调用判完所有候选**（不是每条一次）——省调用，且模型能横向比较谁更相关。
- 判的是「**用户是不是在问她这件事**」，不是「有没有撞到同一个词」；**同话题也算**（用户说"我室友好吵"，她那段是"室友作息健康"→ 该想起来）。
- 输出里模型编的编号会被拦掉（只认候选范围内、且不重复的）；保留条数封顶 `CORPUS_JUDGE_MAX_KEEP = 2`（限制爆破半径）。
- **失败一律返回 []（宁可漏不可错）**——见 1.4。
- `CORPUS_JUDGE=0` 环境变量可整体关掉（快速回滚）。

**判据横向对比实验（`scripts/judge_experiment.py`，corpus 19 条：7 正 / 12 反）：**

| 方法 | 中/该中 | **误报** | 漏 | 准确率 | 召回率 |
|---|---|---|---|---|---|
| 纯余弦 ≥0.48 | 6/7 | **4** | 1 | 0.60 | 0.86 |
| 关键词门（不加 LLM） | 4/7 | 1 | 3 | 0.80 | 0.57 |
| **门 + LLM 判（现方案）** | 5/7 | 1 | 2 | **0.83** | **0.71** |
| BM25 + LLM 判 | 3/7 | **0** | 4 | 1.00 | 0.43 |
| HyDE + LLM 判 | 4/7 | **0** | 3 | 1.00 | 0.57 |
| 余弦+BM25+HyDE **并集** + LLM 判 | 4/7 | **0** | 3 | 1.00 | 0.57 |

**三条结论**：
1. **现方案是这两个任务里最好的**——纯余弦准确率只有 0.60（4 个误报），**加上关键词门升到 0.80** → 关键词门是有价值的。
2. ⚠️ **出乎意料：多路召回取并集，召回反而更差**（0.71 → 0.57）。三路并集最多 18 条候选交同一个 LLM 判——**候选给多了会稀释判定质量**。这反过来验证了 `CORPUS_CANDIDATE_N=6` 不是拍的。**瓶颈不在候选池，在判据本身。**
3. **BM25 / HyDE 是"0 误报但召回腰斩"**（0.43~0.57）。符合"宁可漏不可错"，但漏太多就白做 → 现阶段不值得换。

### 2.2 behavior（行为触发）

**不走向量**。判定分两层，`select_behavior_item(user_msg, behavior_intent, behaviors)`：

| 层 | 来源 | 说明 |
|---|---|---|
| ① LLM 意图（权威） | `classify_l3` 的 `behavior` 字段 | 命中行为名 → 按名字查表 |
| ② 判别词兜底 | `behavior_keywords.json`（21 词） | LLM 判不出但消息含判别词（"你是不是在敷衍我"）→ 保底命中 |

`classify_l3(deepseek_client, user_msg, history_text, behaviors)` 一次调用判出：
- **行为名**（最多 1 个）—— 语义是"这句落在哪个已知情境 → 该怎么做"
- **连续索要**（`same_request`：`{"what", "count"}`）—— 同一次调用顺带判，零额外成本

> ⚠️ **为什么归属交给 LLM、不用 embedding 猜**：embedding 按**句式**聚团——'灰泽满你唱歌好听'（夸）和'灰泽满你怎么又迟到'（质问）句式相同，在向量空间挤成一团，余弦匹配会把夸奖误判成质疑。
> ⚠️ **判别词已退为兜底**：那 21 个词在 150 条真实消息里 **0 次命中**。逐词测：被质疑类"装 2、演 2、敷衍 1"，失约被催类**全部 0**，被越界类**全部 0**——**不是词表写错了，是这几类事在真实对话里几乎不发生**。处置二选一：删（L3 是主判据，一直在工作），或留着但标记"从未被触发"。
> ⚠️ `select_behavior_item` 分数写死 1.0、**没有相似度、没有排名**——它干的是"按名字查表"，不是检索。放进 RRF 会占 top-6 名额（见 2.4 的 `DETACH_BEHAVIOR`）。

**行为注入文本**由 `persona._format_behavior_rule` 生成：`【行为名】+ 触发情境 + 回应模式 + samples`。其中：
- `response` 描述"**做什么**"（什么情境怎么反应），**不规定"用哪个词"**——措辞是台词，归 samples 承担。
  > 踩过：曾把"'呃…'起头"写进 response，配上注入端的强制语，导致同一情境反复触发时每次都同一个开头（14 条回复里 8 条以"呃，"开头，而 86 条真实素材里 **0 条**这么开头）。
- `samples` 给"她真实怎么说话"的示范（来自素材，**允许本土化同义改写**——直播弹幕语境 → 私聊，语境变了要适配）。判据：携带**某一回的具体情境**的样本会被模型当**现在**复用（"明天要搬家"→ 三个月后还在说搬家），要改写成"她一贯如何"。
- `_strip_speaker_prefix`：数据里 samples 的 user 有写"粉丝说：…"的也有裸问题的（不统一），注入模板自己会加"粉丝说："，所以这段前缀在代码侧收掉。

### 2.3 preference / core_story（两路直达）

**preference**（`retrieve_preferences(query, top_n=PREFERENCE_TOP_N=2)`）：
- 判据：`keywords` 子串命中 **或** `pattern` 正则命中（和 terms 同一套）。`load_preferences` 只留"有 text 且有 keywords"的条目。
- **不走向量**——零成本、可解释、可人工审、能写测试。
- **为什么不用向量**：偏好是"类别 + 一串用户能直接说出的词"（食物 / 水果 / 猫狗…），跟 terms 同构。实测余弦的噪声地板 0.565 **插在正例正中间**（正例 0.501/0.552/0.590），任何阈值都分不开。
- 子串法的天花板：只能靠"挑更多具体词"逼近，不可能根治（"吃"会撞"吃什么药/吃瓜"）。写坏的正则不该炸掉整路（`except re.error → pat_hit=False`）。

**preference 判据对比（22 条：10 正 / 12 反）：**

| 方法 | 中/该中 | **误报** | 漏 | 准确率 | 召回率 |
|---|---|---|---|---|---|
| 余弦 ≥0.55（旧方案） | 8/10 | **4** | 2 | 0.67 | 0.80 |
| **子串命中（现方案）** | 9/10 | 1 | 1 | **0.90** | **0.90** |
| BM25 | 3/10 | 0 | 7 | 1.00 | 0.30 |
| LLM 判 | 5/10 | 0 | 5 | 1.00 | 0.50 |

> ⚠️ 子串法在这份标注集上暴露了固有张力（两条错各占一头）：**误报**「感冒吃什么药」（"吃什么"撞"吃什么药"）；**漏**「中秋节了，hzm吃月饼了吗」（关键词表里没有"吃"类泛词）。**改窄会漏、放宽会误报**——这是天花板。

**core_story**（`retrieve_core_stories(query, query_vector, threshold=0.42, top_n=2)`）：
- 判据：与用户消息的向量相似度 ≥ `CORE_STORY_THRESHOLD = 0.42`（**比 corpus/偏好低**，核心故事更容易浮现）。
- 这些是直播以来印象最深的结晶（现 5 条），**独立检索避免被 400+ 条普通背景淹没**。

> ⚠️ **标注集只有 41 条，且边界案例的标签是实验者定的**，直接决定谁赢。扩样 + 人工裁决边界之前，2.1/2.3 的结论只能当**方向**，不能当定论。

### 2.4 RRF 融合 + 条数/字符预算截断

**`fuse_and_truncate(corpus_items, behavior_items=None)`**（`fuse_and_truncate → rrf_fuse → truncate_by_budget`）：

```
rrf_fuse([corpus, behavior])
    score = 权重 / (RRF_K + 路内排名)      # 加权 Reciprocal Rank Fusion
    排序 → 截断到 RETRIEVAL_TOPK = 6 条
    → truncate_by_budget：字符预算贪心保留
        预算 RETRIEVAL_BUDGET_CHARS = 1200 字
        单条上限 MAX_RETRIEVAL_ITEM_CHARS = 300 字
        （超单条上限的条目按 300 计费；预算不够的低优先级条目丢弃）
```

| 常量 | 值 | 作用 |
|---|---|---|
| `RRF_K` | 60 | RRF 平滑常数 |
| `SOURCE_WEIGHTS` | `{"behavior": 1.5, "corpus": 1.0}` | 各路权重 |
| `RETRIEVAL_TOPK` | 6 | 融合后条数硬上限 |
| `RETRIEVAL_BUDGET_CHARS` | 1200 | 融合检索注入字符预算 |
| `MAX_RETRIEVAL_ITEM_CHARS` | 300 | 单条检索结果字符上限 |

> **关键：用"路内排名"而不是绝对分**，所以弱路的第 1 名能压过强路的第 3 名。`SOURCE_WEIGHTS` 就是用来调这个的。
> ⚠️ `SOURCE_WEIGHTS` 实测**不敏感**：81 个权重组合里 77 个并列 47/48，现状就在最优档（有 4 个组合更差 → 判据不是不会失败）。单路扫（behavior 1.0/1.5/2.0、corpus 0.7/1.0/1.4…）**全是 47**。
> ⚠️ **附带发现（比结论本身重要）**：`retrieval-eval` 的判据是"**每一路各自**有没有召回对的条目"，而权重**只影响融合后的排序与截断，不改变任何一路的召回** → 拿 retrieval-eval 扫权重永远是平线。要扫权重得换判据为「融合+截断之后，期望的条目还在不在」。

**`DETACH_BEHAVIOR` 开关（`_detach_behavior_from_rrf`，缺省关）**：
- 关（现状）：`fuse_and_truncate(corpus, behavior)` —— 两路抢 6 个名额。
- 开：`fuse_and_truncate(corpus) + behavior` —— 截断**之后**再追加行为，永不参与名额竞争；名额全还给 corpus。
- 提出缘由：行为/措辞**已经不是检索了**（按 L3 判出的名字**查一条**，没有相似度、分数写死 1.0），把它丢进给"检索"造的排行榜，它**占 top-6 名额**。
- A/B 结论（2026-09-30）：**不删任何东西**；注入量平均 **+6 字**（−10~+24，≈免费）；15 轮真实 A/B 用户判"都差不多"；评测不变（retrieval-eval 47/48、regression 8/8）。
- ⚠️ **那为什么没开**：有个指向"可能有害"的信号没查清——新版让 corpus 多进 1~2 条（名额不再被行为占），素材多了模型可能更容易盯住某一条的开头而更同质；而那条 regression 用例判的正是"反复求交往时不能每轮同一个词开头"。**收益不足以冒这个险**（它不修任何已知故障），按"信号未清就不动"处理。

### 2.5 候选池 vs 判定——两条用例的教训

收尾时照出两条用例，表面上都是"corpus 没召回"，但**一个卡在候选池、一个卡在判定**（**不是同一个病**）：

| 用例 | 卡在哪 | 证据 | 处置 |
|---|---|---|---|
| `co9`「你不是以前有喜欢的男学霸吗」 | ⚠️ **候选池漏了**（不是判据） | 把目标条**手动塞进候选**后，判据**保留了它** | 素材层补 #42 的钩子 `学霸/男学霸`——素材写的是"谎称喜欢一个男**同学**"，用户嘴里的"男**学霸**"不在生成器给的钩子里 |
| `co10`「你就说过最近直播里」 | ⚠️ **判据拒的，而且拒得对** | 目标条**本来就在候选里**，判据说"不相关" | 这句话**没有任何话题**（只说"你说过"）→ 判不出指哪一段；唤起任何一条都是最怕的『想起错的』 |

> **教训**：先用"把目标手动塞进候选"这一步把两者分开，再决定改哪儿。不分开就会一通乱改。
> **一条认知**：关键词表扫描**永远会漏**——漏的词只能靠真实用例补，不是靠扫得更全。

## 4. 注入层 — 最终 messages 的段与顺序

代码入口：`core.build_message_list(...)`（`src/plugins/chatbot/core.py`）。
"17 段"是**逻辑层数**——实际 messages 条数等于"条件成立的段数 + 1"，一般 4~8 条。

### 4.1 三个经常被混淆的概念

| | 指什么 | 本仓的结论 |
|---|---|---|
| **判据** | 这句话该不该唤起某段素材 | 分类 / 关键词 / 向量+LLM 判（第 1、2 节） |
| **形式** | 唤起的素材会被怎么用（照搬？织进去？只当背景？） | 看"是否自足"（见 4.4.1） |
| **位置 / 通道** | 素材以什么身份进入上下文（system 说明 vs assistant 发言；前 vs 后） | 见 4.1.1 |

#### 4.1.1 位置决定视角

```
越靠前 → 越像长期背景（"我一直是这样的人"）
越靠后 → 越像刚刚发生的事（"就在刚才"）
```

所以：**人格放最前，记忆和素材放中间，当前用户消息放最后。**
紧挨用户那句的内容会被读成"刚发生过"，放前面的会被读成"参考资料"——这是同一段内容放在不同位置效果不同的根本原因。

**"通道"比"位置"更要紧**（项目最早的发现）：同一个事实，走 assistant turn **3/5 被采用**；走 system 说明 **0/5**。**"她本人的话"比任何 system 说明都强。**
> ⚠️ 别读成"所有 system 都没用"：3/5 vs 0/5 是拿**同一个"事实"**在两条通道上比出来的。system 里有些东西放进去就会被遵守——**【当前时间】【周表】那类是"信息"**（告诉她一件事），**而"她该怎么说话"那类是"作风"**（要她换一种说法）。**这条结论的适用范围是后者。**

| 【说话节奏】 | 默认短句 / 情绪克制 / 不懂就说不懂 / ⛔不把小事故意讲成故事 / 反问与挑衅式推进 |
| 【自我称呼】 | 日常"hzm/灰泽满" / 轻松"我/小满/满姐" / 脆弱用"我" / **绝不用"她/他"指自己** |
| 【括号与省略号：例外不是常态】 | 括号是"心里话标注"不是默认配置；省略号只在无语到说不出话时用一次 |
| 【行为底色】 | "口是心非"——具体情境怎么反应一律以【行为指令】【固定说法】为准 |

> ⚠️ 【说话节奏】里明写"**私聊里基本没有讲长故事这回事**"——因为**篇幅是域相关的**：素材来自直播（要讲故事撑时长），私聊不是。依据（2026-10-04 实测）：把"戏剧化叙事"当风格注入后，问"今天过得怎么样"从 23 字涨到 41 字，讲一段经历从 46 字涨到 **106 字**，**内容还全是编的**（虚构袋鼠、虚构韩国大妈）。长文本是直播的产物，私聊里几乎不存在。

#### 段 2 — 周表（`schedule.json`）

`load_schedule()` 读 `weekly`（weekday 制，到周自动对，**永不过期**）。**只有 weekly，没有会过期的自由文本字段**（"近况"字段已整条删除）。
作用：被问"明天来吗 / 这周 / 几点播"以它为准——**记忆里带"明天/下周"的话是过去某场直播当时的说法，可能早过期，不能当现在的安排。**
> 消融实测：【周表】净作用 **+88pp**（88% → 0%）。**别改成按需**（没它她就"晚点开，看情况"）。

#### 段 3 — 偏好（`preferences.json`）

命中才注。文本：`【灰泽满的偏好】{category}：{text}；…（这是她稳定真实的偏好，若与直播记忆/聊天记录冲突，以本条为准）`。

#### 段 4 — 核心记忆（`core_story_vectors.json`）

命中才注。文本带明确指示：**被问你的书/事迹时，大方承认、可提议念给 TA 听或说个片段概括，别一口气把原文/全文念出来**（除非对方明确说"念一下"）。
> 消融实测：【核心记忆】净作用 **+38pp**；安慰剂对照下仍 ✅ 内容在起作用。

#### 段 5 — 群聊现场（`group_memory`）

群聊才注。内容：`在场成员：{最近 12 个昵称}。群内近况：{最近 3 条事件，各带"（X前）"}`。
设计：**群 = 好几个不同的绿冻在场，回给刚才直接点名搭话的那位，别把不同的人当成同一个"你"。**
> 坑：群近况事件存了 `t`，以前注入时丢掉 → 上周的事被当"现在"。现在带相对时间注入（和长期记忆 `last_seen` 是同一个坑）。

#### 段 6 — 名词库（terms，见 1.6）

文本：`【灰泽满的世界】{词：意思；被提到时：…；用词规则：…}；…（其中『用词规则』是说话习惯，回复里表达对应概念时主动用她的黑话称呼）`。

#### 段 7 — 当前会话（`session.json`）

文本：`【当前会话】当前话题：… / 本场发生：…`。让模型接得住会话调性。

#### 段 8 — 上次聊过（`previous_session_note`）

上一场会话**已过期**（>12 小时）时注入。**必须在 `probe_session` 之前取**（probe 会把 `last_active` 改写成"现在"）。文本自带定性：`【上次聊过】{X前}你们聊到「…」，当时：…。（隔了这么久，这不是现在正在聊的话题…）`。
> 为什么单独一条、不能并进"当前会话"：那句写的是"你们这一场对话"，把几天前的东西塞进去她会当成现在。

#### 段 9 — 当前时间（`context_probe.get_now_context`）

**每轮都注**（占预算极少）。内容一行：北京时间 + 墨尔本当地时间 + 农历/节气/节日 + 灰泽满所在地（澳洲）+ 真实直播状态 + 天气（按该用户城市，缓存预热）。
- 时间/农历/节气全部本地同步计算（免费、零依赖）；天气走和风（进程内缓存 1 小时）。
- **天气预热**：组消息前异步 `warm_weather` 把城市 LocationID + 天气取进缓存，`build` 时同步读缓存零阻塞。
- **直播状态**读 B站 monitor 的真实状态，避免编造"刚下播/在直播"。骨架明写"直播状态以【当前时间】感知行注入的为准"。
> 消融实测：【当前时间】净作用 **+92pp**——决定性。
> ⚠️ 骨架里【身份】【身份与位置】多处依赖"感知行"：感知行说"没有在直播"就别说"刚下播"。

#### 段 10 — 行为指令（behaviors，见 2.2）

文本：`【当前情境下的行为指令】\n{_format_behavior_rule 生成的内容}`。**这是人格层的另一半**（骨架是第一半），但**不是常驻**——L3 判出情景才注入。16 条里命中哪条注哪条，**含那条的真实原句 samples**。
> 消融实测：【行为指令】净作用 **+55pp**；安慰剂对照下 ✅ 是内容在起作用（不是"删了一段"的副产物）。

#### 段 11 — 相关背景（corpus，见 2.1）

文本开头明写：`【她经历过的相关背景】以下是她过去直播里经历过的事（背景记忆，都是曾经发生的，不是现在）`，并带一长串约束：**别拿背景记忆编当下的因果**——她一贯的毛病（迟到/睡过头/拖延/临时鸽/熬夜）是常态，被问时直接认领常态就好；某次具体的旧记忆只当讲古素材，绝不能拿来当这次的理由去编因果。
> 消融实测：【相关背景】净作用 **+100pp**（4/4 → 0/4，"你多高啊"）——决定性（但只测了 1 个话题）。
> ⚠️ **这段包装语 200 多字，实测管不住模型**（见 4.5）。

#### 段 12 — 长期记忆（见第 5 节）

文本：`【关于这个绿冻的长期记忆】\n{memory_context}`。群聊不建用户记忆卡 → 群聊不注这段。

#### 段 13 — 最近对话记录（`user_history`）+ 防矛盾/防复读

最近 5 轮（10 条）。带"距离上一轮对话已经过去 X 了"（同场对话内 `humanize_gap` 返回空串，不注）。
文本尾部固定带两条约束：
- **【别自相矛盾】**——同一件事的**事实**别前后打架（说过的原因、安排、答应过的事）。**只管事实，不管说法和态度**。
  > 旧的【一致性规则】写的是"借口要与之前保持一致"——那是**直接教它复读**：一旦第一次用了某个借口（"威严""搬家"），规则就把它锁死，错误只固化不自我纠正。改成只约束事实。
- **【防复读】**——用户重复问同一件事时，可以正面回答，但别把上轮那句原样搬出来。
  > 旧的【防复读】豁免条件是"用户没有主动追问时"——而用户反复追问正是复读高发场景，等于在最需要它的地方自动失效。

#### 段 14 — 客观情况（连续索要计数）

`same_request` 且 `count ≥ 2` 才注。文本：`【客观情况】用户已经连续 N 轮在向灰泽满要{what}了（换着说法也算同一件事）。前面 N-1 轮都没有答应。`
> **为什么必须有（2026-10-04 从真实记录发现）**：上下文只带最近 10 条，**跨轮的连续索要她完全看不见** → 每轮都当成"第一次被要" → 换着理由挡 5 轮后突然松口，松口之后又失去"我从没答应过"的立场（3076669330 要"宝宝"/要语音两段都是这样）。
> ⚠️ **只给事实**（第几轮、之前在要什么），**不给"该不该答应"**——"怎么应对"是 behaviors 的事；而且实测"管怎么用"的说明无效、事实类信息有效。

#### 段 15 — 批消息的归纳（`batch_summary`）

一批超过一条才注（`summarize_batch`）。文本：`【这批消息的归纳】…`。**原文仍完整保留**（归纳只是理解整批的提示层，失败返回空串）。

#### 段 16 — 用户这条消息的语境 / 用户发了表情（`query_hint`）

用户消息 ≤4 字（或指代性消息、纯表情）时，把扩充后的完整语义作为提示给模型（**正文仍是原 msg**）：
- 纯表情消息（emoji / [表情：xx]）→ `【用户发了表情】…`：**以这个表情本身的情绪为准**，别读成别的情绪。**只做"别读错情绪"的正确性约束，不规定她该怎么反应**（"什么情绪 → 怎么回应"属于数据层，由 behaviors 承担）。
  > 曾在这里写过"委屈 → 该放软、别嘴硬顶着"，那是提示词补丁，已回退。
- 非表情短消息 → `【用户这条消息的语境】…（上面是这条消息在当前语境下的完整意思——短消息或指代性消息需要结合前文才能理解，按这个理解回复）`。

#### 段 17 — user（用户真正说的那句话）

`final_user`：图片消息把视觉描述并入（`[图片：{desc}]`）；正文是原 msg。**最后一条，最"当下"。**

#### 4.4.1 形式实验——同一个事实写成不同形式会怎样（`scripts/form_experiment.py`）

实验设计：用**她数据里没有的**事实（否则基线会泄漏）；只变一个变量（其余走真实链路 `build_message_list`）；不写任何记忆。主判据是**特征短语的逐字复读率**。

事实 =「最喜欢的数字是 7」，提问「你最喜欢哪个数字啊」，各 16 次：

| 形式 | 对应角色 | **采用率** | **逐字复读率** |
|---|---|---|---|
| 不注入（基线） | — | 9/16（瞎猜） | 0/16 |
| system 第三人称陈述 | corpus | **16/16** | **10/16** |
| system 事实条目 | preferences | **16/16** | 5/16 |
| system 词表（**自足**，拼起来是一句完整的话） | — | **16/16** | **16/16** |
| system 指令式 | behaviors | **16/16** | **16/16** |
| **assistant 问答对** | （原 voice_samples） | **15/16** | **0/16** |
| system 碎片词表（**不自足**，只能织进去的措辞） | （原 phrases） | 5/16 | **0/16** |
| 同"词表"内容，换成 corpus 式包装 | — | 16/16 | **16/16** |
| 问答对·user 改成情境描述 | — | 16/16 | **0/16** |
| 只有 assistant（无配对 user） | — | 16/16 | 7/16 |
| system 纯情境描述（无指令语气） | — | 16/16 | **15/16** |

**三条结论：**

1. **传不传得进去，从来不是问题。** 各形式**全都 15~16/16**，基线只有 9/16。**只要注入了，内容就进得去。**
2. **真正分得开形式的是"会不会被整句搬走"。**
   ```
   自足 → 被整句搬走       词表 16/16 ｜ 指令 16/16 ｜ 陈述 10/16
   不自足 → 只能织进新句     碎片 0/16
   问答对 → 既不逐字又传得进  问答对 0/16（且采用 15/16）
   ```
   > 修正了一条旧结论：旧说法是"phrases 给词表 → 只能织进句子"，但实验里"**自足**词表" **16/16 逐字**。**真正的变量不是"哪个文件"，是"注入的那段是否自足"。**
3. **assistant 问答对有独家特性，也有独家副作用。** 独家特性：唯一"既传得进内容、又不逐字复读"的形式。独家副作用：**她会以为"刚说过"**（回复里大量出现"刚不是说了嘛""问两遍干嘛"）。

**⚠️ 两种"以为用户刚说过"的修法测过（2026-09-27）：**

| 形式 | 采用 | 逐字 | **以为"刚说过"** |
|---|---|---|---|
| assistant 问答对 | 16/16 | 1/16 | 8/16 |
| 问答对·user 写情境描述 | 16/16 | 0/16 | **12/16** ⚠️ |
| 只有 assistant（无配对 user） | 16/16 | 7/16 | **1/16** |

> 把 user 改成情境描述**治不了撞车，反而更糟**（8→12）：撞车的根源是**话题重复**不是措辞重复。真想治，得**去掉 user 字段**（1/16），代价是逐字率升到 7/16——**这是个可量化的取舍**。

#### 4.4.2 空轮次实验（否定结果，但很有价值）

**疑问**：素材层全空的轮次占 45%，那时她只有基础人格，条靠规则答，会不会变成"一个遵守规则的人"？试：空轮次垫 1~2 条随机风格样本。

| 条件 | 自称率 | 「我」率 | 括号率 | 叹号率 | 均长 |
|---|---|---|---|---|---|
| 现状（不垫） | 12% | 0% | 0% | 0% | 20.8 |
| 垫 1 条随机样本 | 12% | 0% | 0% | 0% | 17.8 |
| 垫 2 条随机样本 | **6%** ↓ | 0% | 0% | 0% | 20.2 |

**风格指标全部持平，自称率反而降了**，还出现内容跑题（样本的内容被当回答）。
> **结论：垫随机样本没用，还有跑题风险。** 它反过来证明——**45% 的空轮次不是问题，骨架在管用**。括号率 0%、叹号率 0%、长度 20 字，说明"别堆感叹号""别用括号"这些**否定式规则是确实在起作用的**。
> 推论：那条"否定式约束弱"的教训，适用范围是**"管内容信不信"**（如"别整段复述"，无效）；对**"管说话风格"**它是有用的。两个场景别混。

**corpus 的注入还高度集中**：前 10 条占了全部注入次数的 44%。
**一条贯穿全部结论的规律：绝大多数素材从没被用到过**（corpus 89% / terms 88% / legendary 90% / behaviors 73% 没用过）。
> ⚠️ 但两种"没用过"性质完全不同：**corpus（语义）会漏** → 可能是判据问题（改判据/给入口）；**terms / legendary（确定性）不会漏** → 用户没说那些词，是内容问题（条目没问题，只是没被验证过）。
> **核心洞察：从没被触发过的条目 = 从没被验证过的条目。** 处置方式是**造能触发它们的消息去测**，不是裁库。

#### 4.4.5 库越大越好吗——不是（实测）

| 库大小 | 10 | 50 | 100 | 200 | 322 |
|---|---|---|---|---|---|
| 噪声地板 | 0.420 | 0.435 | **0.471** | 0.471 | **0.474** |
| 正例「你多高啊」 | 0.443（**高于地板**） | | 0.443（**已低于地板**） | | 0.443 |

**库涨到约 100 条时，真信号就沉到噪声地板下面了。** 但边际代价是次线性的（10→322 条只涨 0.054）——所以结论不是"该删到 50 条"，而是"**该问每条有没有召回入口**"。

### 4.5 ⭐ 包装语无效（最反直觉的发现）

**同样内容（"7，一直排第一"），只换外面那句说明：**

```
【她的固定说法】…用这些原话组织     +「7，一直排第一」 → 逐字 16/16
【她经历过的相关背景】…不整段复述   +「7，一直排第一」 → 逐字 16/16   ← 一模一样
```

**包装语对"抄不抄"零作用。**
这条很重要，因为项目里**每个注入层都写了长篇包装语**（corpus 那条 200 多字），以为能规定模型怎么用这段内容——**实测它管不住模型**。

> **结论：文件的"角色"不写在包装语里，写在内容形式里。**
> 想要她"当事实知道" → 写成事实条目；想要"当风格学" → 写成问答对；想要"当台词说" → 写成自足句（**它一定照抄**）；想要"当措辞用" → 写成碎片。
> ⚠️ 边界：这**不等于"包装语全无用处"**——它可能仍在管别的事（如时间语义、优先级声明）。但**在"怎么用这段内容"这件事上，实测无效**。机制上：模型看到上下文里的问答对，走的是 **induction head 的 pattern completion**（"续写"），不是"服从指令"。**举证责任应该反过来：想让模型怎么做，先改形式，别先加说明。**

## 5. 记忆层

她有四层记忆 + 一张卡，各解决一个不同的问题。**根目录的 `memory_manager.py` 是长期卡的真身**，其余在 `src/plugins/chatbot/`。

### 5.1 三层 + 一张卡

```
                    ┌─────────────────────────────────────────────┐
 长期（一张卡）      │ 根 memory_manager.py                         │  user_memory/long_term.json
   "他是谁"          │ 用户画像：名字/城市/印象/事实/承诺/重要时刻   │  异步提取、跨会话
                    └─────────────────────────────────────────────┘
 会话（episodic）    session_memory.py  ·  "这一场在聊什么"           user_memory/session.json
                    topic + events + last_active                    对话前同步探测
 群（轻量）          group_memory.py    ·  "这个群是谁、聊过啥"       user_memory/groups.json
                    members + events（带时间戳、冷却）               只在本群注入
 短期（碎片）        memory.py          ·  "最近几句原话"             user_memory/short_term.json
                   最近 5 轮（10 条）原文，带时间戳                 每轮回复后追加
```

### 5.2 各存什么、什么时候读、什么时候写

| 层 | 文件 | 存什么 | 何时**读**（注入） | 何时**写** |
|---|---|---|---|---|
| **长期卡** | 根 `memory_manager.py` → `user_memory/long_term.json` | 用户画像（见 5.3） | 每轮回复前 `build_memory_context(card)` →【关于这个绿冻的长期记忆】 | 每轮回复后**异步** `update_memory_task`（LLM 提取增量）；群聊不建卡 |
| **会话** | `session_memory.py` → `user_memory/session.json` | `topic`（当前话题）+ `events`（本场关键事件，≤6）+ `last_active` | 每轮回复前 `build_session_context` →【当前会话】；过期则降级成【上次聊过】 | 每轮**回复前同步** `probe_session`（判断转话题/累积事件/扩充短 query） |
| **群** | `group_memory.py` → `user_memory/groups.json` | `members`（id→昵称）+ `events`（群近况/梗，≤20，带 t） | 群聊回复前 →【群聊现场】 | 群聊里每批 `upsert_members`；`_flush` 里写 `add_event`（冷却 `GROUP_EVENT_COOLDOWN=300s`） |
| **短期** | `memory.py` → `user_memory/short_term.json` | 最近 `SHORT_MEMORY_LINES=10` 条 `{t, text}`（5 轮） | 每轮 `get_user_history(user_id)` →【最近对话记录】 | 每轮回复后 `append_user_history`（写清洗后的回复，防自我强化回路） |

**几个关键设计点：**

- **会话探测在"回复前"同步跑**（不是回复后异步）——这样第 N 轮注入的就是第 N 轮自己的话题，不滞后一轮。一次 LLM 调用同时干三件事：判断是否转话题 / 累积事件 / 扩充短 query。
- **上一场会话（>12 小时）不丢也不当现在**：`SESSION_STALE_SECONDS = 12h`。过期的不当【当前会话】，但降级成 `previous_session_note()` 的【上次聊过（X 前）…】，并**明说"这不是现在正在聊的话题"**。`previous_session_note` **必须在 `probe_session` 之前调**（probe 会把 `last_active` 改写成"现在"）。
- **拿不到时间戳的一律按冷场处理**（老记录/手改记录没有 `last_active`）——旧写法缺字段的记录会直接跳过检查、永久免疫，永远被当【当前会话】注入。
- **时间戳到处都在参与提示**：长期卡的 `last_seen` →"距上次跟TA说话已经过去X了"；群近况事件带"（X前）"；短期历史带"（距离上一轮对话已经过去X了）"；重要时刻带"（X前）"。共用一个 `humanize_gap`（<90 秒返回空串，同一场对话不必提）。历史上多处"存了时间戳、注入时丢"，都补上了。
- **写入短期记忆用清洗后的版本**：否则她带换行/多括号的原始输出会存进记忆、再作为 few-shot 喂回去，形成自我强化回路。
- **兜底文案绝不进记忆**：`is_fallback_reply` 命中则整轮不记（含用户的这句）——一次上游抖动曾让她永久"记得自己说过"一句故障文案。
- **群聊不接话时也记（只记用户侧）**：她"看到了、只是没说"；不记的话下一轮判定看不到上下文，她会开始"装作知道上文"。
- **主动说的话也要记**（`append_bot_message`）：主动发出去的 API 消息不会作为事件回来，粉丝顺着回她时她完全不知道对方在说什么。
- **短期记忆的两种行形态**：旧数据是裸字符串，新数据是 `{"t": epoch, "text": "…"}`；`_entry_text` 对外一律还原成字符串，调用方无需知道存法。
- **并发写用进程内文件锁**（`threading.Lock`）保证"读-改-写"原子化，防多消息并发互相覆盖。

### 5.3 记忆卡字段与合并规则

**卡（card）字段：**

| 字段 | 含义 | 合并规则 |
|---|---|---|
| `total_interactions` | 交互次数 | 每次 +1 |
| `last_seen` | 最后见面时间 | 每次写"现在" |
| `impressions` | 印象标签（如"夜猫子"） | 已存在 → confidence +0.1（封顶 1.0）；新标签 → confidence 0.8 |
| `user_facts` | 用户长期事实（如"在广州上班"） | 按 `fact` 去重后追加 |
| `self_facts` | 她已透露给 TA 的事实 | 按 `fact` 去重后追加（**V1 起不再从 AI 回复提取**，防自嗨污染） |
| `significant_moments` | 重要时刻（`{date, summary}`） | 追加，只保留最近 **5** 条 |
| `weather_city` | 用户所在城市 | 覆盖（用户换城市则更新；出差/旅游不算） |
| `user_name` | 用户希望被称呼的名字 | 覆盖 |
| `promises` | 她答应过用户的事 | 按 `promise` 去重，保留最近 **5** 条 |

**合并纯函数 `merge_memory_card(card, updates)`**（`memory_manager.py`，不做任何 IO）：
1. **先清洗 updates**：值为字符串 `"null"/"None"/空串` 的字段**直接丢弃**（模型常把"无"写成字符串而非 JSON null——曾导致上下文出现"这个绿冻在null"）。
2. 基础统计：`total_interactions +1`、`last_seen = 现在`。
3. 逐字段合并（见上表）。
4. **supersede**：用户明确说某已知信息已变（"我现在不上班了""我不在广州了"）→ 从 `impressions` / `user_facts` 里删掉对应旧条目。**防旧标签永远残留。**
5. `update_user_memory(user_id, updates)`：读-改-写全程持锁。

**注入时过滤（`build_memory_context`）**：
- 只注 `confidence > 0.6` 的印象标签。
- `_not_null_str` 兜底再滤一道历史遗留的 'null'。
- 距上次聊天：`format_last_seen_gap(last_seen)` → "距上次跟TA说话已经过去X了"（时间戳一直在存，但以前从不注入 → 模型分不清"刚刚说的"和"半个月前说的"）。
- 重要时刻用 `format_day_gap`（按天，不是按秒）——纯日期没有小时精度。

**提取流程（`update_memory_task`，异步后台）**：
- **密度门控**：消息 <4 字、纯表情 → 不提取（省成本减噪音）。
- 用**可读画像摘要**（`_format_profile_summary`）喂模型而非 JSON dump——模型读可读画像才能可靠 dedup（判断"已知道没"）和冲突检测。
- **强制规则**：`new_self_fact` 一律返回 null，**只提取关于用户的信息**（防从她的回复里提取自我披露污染人格）。
- 首次失败（多为 JSON 不规范/偶发）→ 严格格式重试一次；不阻塞聊天。
- LLM 提示词里的分层原则：**不可变身份**（名字/生日/过敏）一次就可记；**可变偏好/状态**（职业/爱好/居住）要明确陈述或重复提到才记；**一次性心情/状态**（"今天好累""刚下班"）不记。**保留限定词**（"在XX公司做设计"不是"做设计的"）。

### 6.2 几个阈值的落点（`constants.py`）

| 常量 | 值 | 动它的后果 |
|---|---|---|
| `RAG_THRESHOLD` | 0.48 | corpus 语义下限；调低靠关键词门挡噪声，调高会卡掉自然问句 |
| `CORPUS_KEYWORD_FLOOR` | 0.12 | **只决定"值不值得让 LLM 看一眼"**。⚠️ 别想靠调它挡误报——误报重叠度反而更高（见 2.1） |
| `CORPUS_STRONG_KEYWORD` | 0.8 | 强关键词重叠（专名/罕见短语）——50 条评测上一次没触发，纯冗余 |
| `CORPUS_CANDIDATE_N` | 6 | 交给 LLM 判的语义候选条数（6 条判得准，多了稀释注意力） |
| `CORPUS_LEXICAL_EXTRA_N` | 6 | 词面补位封顶（防判定池灌爆） |
| `CORPUS_JUDGE_MAX_KEEP` | 2 | 判定最多保留几条（限制爆破半径） |
| `CORE_STORY_THRESHOLD` | 0.42 | 核心故事比 corpus 更容易浮现 |
| `PREFERENCE_TOP_N` / `CORE_STORY_TOP_N` | 2 / 2 | 两路直达的条数上限 |
| `RETRIEVAL_TOPK` / `RETRIEVAL_BUDGET_CHARS` / `MAX_RETRIEVAL_ITEM_CHARS` | 6 / 1200 / 300 | RRF 融合后的条数/字符预算 |
| `RRF_K` | 60 | RRF 平滑常数（不敏感，别动） |
| `SOURCE_WEIGHTS` | behavior 1.5 / corpus 1.0 | 实测不敏感（77/81 组合并列），别没事去动 |
