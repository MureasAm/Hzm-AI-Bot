## 1. 这集只回答一个问题

**一个角色机器人，究竟怎样从仓库里的文件，走到最终的一条回复？**

视频完整讲清：

```text
文件中的内容
  → 判断这一轮需不需要
  → 取出相关内容
  → 转换成模型能读到的 messages
  → 模型生成
  → 回复清洗、发送、记忆回写
```

其中重点强调两份人格核心：

- `persona/core/system_prompt.txt`：稳定骨架，决定她始终是谁；
- `persona/behavior/behaviors.json`：情景行为，决定这个人在当前处境下怎么反应。

这两份文件负责“说话方式与行为风格”的最小核心，但**不等于整个角色系统**。角色事实、用户记忆、当前时间、天气、图片、群聊现场等内容仍由其他层提供。

### 1.1 本集最终结论

结尾必须让观众记住下面两句话：

> 基础提示词负责让她始终是同一个人；behavior 负责让这个人在不同情景下做出不同反应。

> 文件名模型看不见。模型真正读到的，是内容的文本形态、message role、注入位置和当前对话。

### 1.2 不要作出的过度宣称

不要说：

- “两个文件就能完整还原一个人”；
- “behavior 理论上覆盖了所有可能回复”；
- “例句越多一定越像”；
- “每轮都会把全部文件注入”；
- “Memory V2 已经正式参与线上回复”。

可以说：

- 当情景覆盖持续完善时，`system_prompt + behaviors` 可以覆盖越来越多的风格反应；
- few-shot 的价值不只是模仿句子，而是把真实示范绑定到正确情景；
- 其他层补充的是事实、记忆和现场，而不是再造一套人格；
- Memory V2 当前仍是影子模式，本集只展示现行有效链路。

## 2. 叙事语气：技术准确，但像活人在讲

### 2.1 旁白视角

采用混合视角：

- 角色感与转场：灰泽满第一人称；
- 架构事实与实验结果：项目作者/工程视角；
- 音色始终使用灰泽满 GPT-SoVITS，不切换中性配音。

允许出现的表达：

> “模型不是把整个文件夹吞下去。它甚至不知道这些文件叫什么。”

> “先别急着看那十几段上下文。最核心的其实就两件事：我是谁，还有这种时候我会怎么做。”

> “不是，这里没发图，图片理解那一层就别硬挤进来了。”

不允许把整篇旁白写成连续段子。建议每 20～30 秒最多一次轻吐槽；严肃结论出现时，让画面和旁白都安静下来。

### 2.2 活人感制作规则

1. 旁白保留少量停顿、改口、自我拆台，但不要故意添加大量口癖。
2. 重点结论出现前允许留 6～12 帧空拍或停顿。
3. 同一时刻只让一个层面抢注意力：声音在吐槽时，画面动作要简单；画面在做复杂变换时，旁白要短。
4. 立绘不常驻。只在开场、吐槽、例句发声、章节转场和结尾出现。
5. 不使用“发光 AI 大脑、赛博神经网络、粒子数据流”等模板化 AI 视觉。
6. 动画不全是平滑淡入：允许文件卡被挤开、便签贴上去、灰色卡片留在未命中区，但整体不能像综艺花字。

## 4. 开场三板对照：必须是真实生成，不是摆拍

### 4.1 固定输入

```text
你今天唱得特别好，我真的很喜欢。
```

### 4.2 三种版本

三栏从出现时就直接标注，不制造猜谜：

1. **裸模型**：只给用户消息；
2. **仅基础提示词**：`system_prompt + user`；
3. **基础提示词 + behavior**：加入当前分类器真实选中的“被夸时如何回应”behavior。

三版必须使用同一个模型与相同生成参数。建议读取运行时真实配置，不在视频脚本里另造一套参数。当前项目参数基线为：

```text
temperature = 0.85
frequency_penalty = 0.3
max_tokens = 150
thinking = disabled
```

制作前再次以代码中的 `constants.py` 和 `config.py` 为准；如果参数已经变化，更新数据文件与本说明，不要默默沿用旧值。

### 4.3 生成协议

每种版本至少运行 5 次，原始结果全部保存。建议新增：

```text
video/data/ep01/persona-comparison.json
```

建议结构：

```json
{
  "generated_at": "ISO 时间",
  "model": "实际模型名",
  "params": {
    "temperature": 0.85,
    "frequency_penalty": 0.3,
    "max_tokens": 150
  },
  "input": "你今天唱得特别好，我真的很喜欢。",
  "variants": [
    {
      "id": "bare",
      "label": "裸模型",
      "messages": [],
      "runs": ["原始回复1", "原始回复2"],
      "selectedRun": 0,
      "selectionReason": "选择理由"
    }
  ]
}
```

规则：

- 不人工改写模型回复；
- 可以经过项目现有 `clean_reply`，但同时保留 raw 与 cleaned 两个字段；
- 禁止为裸模型故意挑最差结果、为最终方案挑最好结果；
- 选用结果时写明理由，并在制作资料中保留 15 条完整输出；
- 不用 LLM judge 宣称“更像”，视频只展示可观察差异：是否礼貌感谢、是否只有泛化嘴硬、是否形成 behavior 规定的反应动作。

### 4.4 画面

- 三栏等宽消息面板，同时使用同一个模型标识；
- 用户消息在三栏顶部完全相同；
- 回复逐句出现，必须播放对应的灰泽满语音；
- 三栏出现顺序为裸模型 → 基础提示词 → 基础提示词加 behavior；
- 不用红叉/绿勾粗暴判优；使用关键词标注差异：`礼貌回应`、`稳定骨架`、`完整反应动作`。

### 4.5 旁白任务

旁白只需要完成三件事：

1. 指出三栏是同一个模型；
2. 指出改变的是模型当时看到的上下文；
3. 提出本集问题：“这些文件到底怎样走到回复里？”

不要在开场解释 RAG、embedding 或 JSON。

## 5. 两份人格核心

## 5.1 `system_prompt.txt`：稳定骨架

画面从三栏中间版本抽出一张 `system_prompt.txt` 文件卡，展开当前真实章节：

```text
核心人格
身份：人设 × 真实经历
身份与位置
说话节奏
自我称呼
括号与省略号
行为底色
```

本段必须讲清：

- 它每轮常驻；
- 它规定不应该随话题变化的稳定事实和表达边界；
- 它擅长保证“始终是同一个人”；
- 它不适合穷举每一种具体人际情景；
- 它不是“越长越好”的角色说明书。

建议画面：

- 左侧文件目录，右侧把章节压成一张人物骨架图；
- “身份”“自称”“节奏”等标签固定在骨架上；
- 用户输入变化时骨架保持不动。

## 5.2 `behaviors.json`：当前情景下怎么反应

固定使用三个术语：

```text
情景 → 反应 → 例句
```

画面拆开一条真实 behavior，但不把整个 JSON 一次铺满：

1. **情景**：用户是在真诚夸她唱得好；
2. **反应**：先压低评价或挡回去，被夸真了以后短暂别扭，再漏一点软话；
3. **例句**：真实素材展示这种动作由灰泽满做出来是什么质感。

旁白核心句：

> “情景负责选对抽屉，反应负责告诉模型往哪走，例句负责告诉它，这个动作由灰泽满做出来，究竟是什么质感。”

必须解释 few-shot，但不要讲成“复制几个句子”：

- few-shot 给模型的是示范；
- 示例必须绑定正确情景；
- behavior 不是固定回复表；
- 示例可以影响节奏、转折和动作形态，但最终回复仍根据当前用户消息生成。

### 5.3 历史演变只占一句

旧 `traits/styles/voice_samples/phrases` 只作为 15～25 秒的背景，不展示失败案例：

> “以前这些职责被拆在更多文件里。现在该留下的稳定内容进入骨架，该留下的真人示范按情景并进 behavior。”

画面可以让旧文件卡缩成两摞并分别并入 `system_prompt` 与 `behaviors`。不要做“垃圾桶式嘲讽”，也不要展开旧机制细节。

## 6. 关键转折：文件不是模型输入

### 6.1 本段论点

```text
文件 = 人维护内容的单位
messages = 模型实际接收的单位
```

模型不知道：

- 文件路径；
- JSON 文件名；
- 这段文字最初属于哪个目录。

模型能看到：

- 文本内容；
- `system/user/assistant` role；
- 内容在 messages 中的位置；
- 当前消息与历史上下文。

### 6.2 画面变换

文件卡进入一个“formatter”区域，出来后变成 messages 卡：

```text
system_prompt.txt
    ↓ load + format
{ role: "system", content: "..." }
```

```text
behaviors.json 中被选中的一条
    ↓ format_behavior_rule
{ role: "system", content: "【当前情境下的行为指令】..." }
```

禁止画成“文件直接飞进大模型”。中间必须出现“读取、判断、格式化”三个动作。

## 7. 三类内容：人格、事实、现场

全片固定色彩语义：

| 分类 | 含义 | 建议颜色 |
|---|---|---|
| 人格 | 她会怎样反应 | 紫色/玫红 |
| 事实 | 她知道什么 | 蓝色/青色 |
| 现场 | 此刻发生了什么 | 绿色/橙色 |

### 7.1 人格

- `system_prompt.txt`
- `behaviors.json`

### 7.2 事实

- `terms.json`：词、人物和梗是什么意思；
- `preferences.json`：灰泽满稳定的偏好；
- `core_stories.json`：最深刻、最常被提及的核心经历；
- `statement_final.json`：过去直播中发生过的背景事实，即 corpus；
- `schedule.json`：当前周表；
- `legendary.json`：固定梗与直接回复路径。

### 7.3 现场

- 用户长期记忆；
- 会话记忆；
- 最近几轮短期原文；
- 当前时间、天气、直播状态；
- 群聊成员和群近况；
- 图片描述；
- 一批消息的归纳；
- 指代性短消息补全；
- 连续索要次数。

注意：用户长期记忆虽然跨会话保存，在这套分类中仍属于“面向当前用户的上下文”，不是灰泽满的人格文件。

## 8. 四种判别方式

先讲人话问题，再显示技术名词：

| 人话问题 | 方法 | 典型内容 |
|---|---|---|
| 每轮都需要吗？ | 常驻 | system prompt、周表、当前时间上下文 |
| 消息里明确提到了吗？ | 关键词/正则 | terms、preferences、corpus 钩子、legendary 粗筛 |
| 意思相近吗？ | 向量召回 | corpus 候选、core stories |
| 这是哪种人际情景，候选是否真的相关？ | LLM 判断 | behavior 分类、corpus 确认、歧义词确认 |

### 8.1 画面结构

建立四个可重复使用的 Gate 组件：

```text
AlwaysGate
KeywordGate
VectorGate
LlmGate
```

文件卡进入对应 Gate：

- 命中：点亮并进入“待注入”轨道；
- 未命中：保持灰色，移入“本轮不注入”区域；
- 失败降级：使用小标签说明是“宁可漏”还是“宁可放行”，但本集不展开异常处理。

### 8.2 准确性边界

不要说“每个文件只使用一种判别方式”。部分路径是组合：

- corpus 会有语义候选、词面补位与 LLM 确认；
- legendary 是关键词/正则粗筛后再做语境确认；
- behavior 以 LLM 情景分类为主，另有确定性兜底。

视频图形可以把主入口画粗、辅助入口画细。

## 9. 文件与内容形式：5:25–7:40

这一段不是逐文件念 README，而是回答：**什么内容用什么形态进入模型？**

### 9.1 重点讲透

#### `system_prompt.txt`

- 判别：常驻；
- 内容形式：稳定说明；
- 注入：首条 system message；
- 作用：人物骨架与表达边界。

#### `behaviors.json`

- 判别：当前消息的人际情景；
- 内容形式：情景—反应—例句；
- 注入：`【当前情境下的行为指令】` system 块；
- 作用：让稳定人格在具体处境中做出动作。

#### `statement_final.json` / corpus

- 判别：向量候选 + 词面补位 + LLM 确认；
- 内容形式：过去发生过的事实陈述，不是可直接复用的当前回答；
- 注入：`【她经历过的相关背景】` system 块；
- 作用：让她记得经历，但不能把旧事编成现在的原因。

#### 用户记忆

本集只讲现行层次和注入作用，不展开 Memory V2：

- 长期：用户是谁、稳定事实、承诺；
- 会话：这一场正在聊什么、发生过什么；
- 短期：最近几轮真实对话原文与时间间隔。

第二集再解释旧结构与 Memory V2 影子方案。

### 9.2 讲清职责和判据

每张卡控制在 8～12 秒：

- `terms.json`：懂词；
- `preferences.json`：稳定偏好；
- `core_stories.json`：最深的经历；
- `schedule.json`：当前周表；
- `legendary.json`：固定梗直接路径。

### 9.3 只在最终 messages 图中出现

- 时间、天气、直播状态；
- 群聊现场；
- 图片描述；
- 批量归纳；
- 短 query 补全；
- 连续索要次数。

这些卡片出现时只显示“来源 → 注入段名”，不再解释内部实现。

## 10. 结尾完整链路演示

## 10.1 固定演示现场

所有数据均为虚构、固定和可复现：

```text
时间：周四 18:40
天气：广州，小雨
周表：周四 19:00 开播
用户：阿澈（虚构），常住广州
会话话题：用户在磨灰泽满念《乌色月》
最近对话：用户此前已经索要过两次朗读
```

建议 fixture：

```text
video/data/ep01/full-trace-fixture.json
```

必须包含：

```json
{
  "fictional": true,
  "clock": "固定 ISO 时间",
  "weather": {"city": "广州", "text": "小雨"},
  "userProfile": {"name": "阿澈", "city": "广州"},
  "session": {"topic": "用户在磨灰泽满念《乌色月》"},
  "recentTurns": [],
  "incomingBatch": []
}
```

不要读取或改写真实 `user_memory/`、`data/chat_log/`。

## 10.2 当前批次

用户连续发送：

```text
满神，我这边还在下雨，刚下班
你今晚几点播来着？
下播后念一段《乌色月》给我听呗，这都第三遍了
```

由读秒窗口合成一批，不压成一句人为的超长问题。

## 10.3 预期亮起的路径

| 内容 | 为什么 |
|---|---|
| system prompt | 常驻 |
| schedule | 固定演示周表 |
| terms | “满神”“乌色月”等词条实际命中情况 |
| core story | 《乌色月》相关核心经历 |
| behavior | 用户要求她做一件事/反复索要的情景 |
| 用户长期记忆 | 名字、城市 |
| 会话记忆 | 正在磨她念作品 |
| 短期记忆 | 前两次索要与此前回复 |
| 当前时间/天气 | 固定的周四 18:40、广州小雨 |
| 连续索要 | 第三次 |
| 批量归纳 | 三条消息属于同一批 |

### 10.4 不应强行命中的路径

| 内容 | 画面 |
|---|---|
| 群聊现场 | 灰色，标注“私聊，本轮不注入” |
| 图片描述 | 灰色，标注“无图片” |
| preference | 按真实判别结果，不相关就保持灰色 |
| corpus | 按真实召回与 LLM 确认结果，不预设必须命中 |
| legendary | 没有真实触发就不亮 |

关键旁白：

> “完整链路不是把所有文件都塞进去。真正完整的是：每一层都有机会判断，而不相关的内容能够保持沉默。”

## 10.5 数据捕获要求

画面必须来自真实项目逻辑产生的 trace，不允许手工伪造“命中”：

1. 使用固定 fixture 替换时钟、天气和用户存储；
2. 调用真实会话探测、检索、分类和 `build_message_list`；
3. 保存每一步输入、命中、未命中和最终 messages；
4. 对所有用户数据做虚构标记；
5. 将产物写入 `video/data/ep01/full-trace-result.json`；
6. Remotion 只读结果文件，不在渲染过程中调用模型或网络。

建议结果结构：

```json
{
  "fixtureId": "ep01-full-trace-v1",
  "decisions": [
    {
      "source": "behavior",
      "method": "llm",
      "hit": true,
      "reason": "已脱敏的简短解释"
    }
  ],
  "messages": [],
  "rawReply": "",
  "cleanedReply": "",
  "delivery": {"mode": "text|voice", "parts": []}
}
```

## 11. 输出侧：只预告，不抢第三集内容

本集结尾展示正确顺序：

```text
最终 messages
  → generate_reply
  → 防复读检测，必要时重新生成
  → clean_reply
  → should_voice
      ├─ 成功：GPT-SoVITS → QQ 语音条
      └─ 不走语音：split_reply → 多个 QQ 文字气泡
  → 写回短期/长期记忆
```

注意：语音成功时不会继续发送拆分文字；不要画成“先拆文字，再顺便生成语音”。

画面只需展示：

1. 一段模型原始回复；
2. 清洗后的文本；
3. 文字拆分或语音二选一；
4. 一个“代码工程篇继续”的提示。

不要在本集展开 `split_reply` 正则、TTS HTTP 请求、缓存或重试逻辑。

## 12. Remotion 工程方案

## 12.1 不覆盖现有样片

现有 `HazelInjectionExplainer` 含旧架构内容，只作为历史样片和组件参考。新增独立 composition：

```text
video/src/episodes/ep01/
├── Ep01PersonaInjection.tsx
├── ep01-narration.json
├── ep01-fixtures.ts
├── scenes/
│   ├── ColdOpenScene.tsx
│   ├── SystemPromptScene.tsx
│   ├── BehaviorCoreScene.tsx
│   ├── FilesToMessagesScene.tsx
│   ├── ThreeDomainsScene.tsx
│   ├── FourGatesScene.tsx
│   ├── ContentFormsScene.tsx
│   ├── FullTraceScene.tsx
│   ├── ReplyOutputScene.tsx
│   └── ClosingScene.tsx
└── components/
    ├── BehaviorAnatomy.tsx
    ├── DecisionGate.tsx
    ├── FileCard.tsx
    ├── HazelAvatar.tsx
    ├── InjectionTrace.tsx
    ├── MessageCard.tsx
    ├── PersonaComparison.tsx
    ├── ReplyPipeline.tsx
    └── TaxonomyMap.tsx
```

在 `Root.tsx` 中新增 composition，例如：

```text
id = HazelBotEp01PersonaInjection
width = 1920
height = 1080
fps = 30
duration = 由 ep01-narration.json 计算
```

旧 composition 保留，便于对照和复用。

## 12.2 数据与画面分离

Remotion 组件不得硬编码实验回复和 trace 结果。统一读取：

```text
video/data/ep01/persona-comparison.json
video/data/ep01/full-trace-fixture.json
video/data/ep01/full-trace-result.json
video/src/episodes/ep01/ep01-narration.json
```

所有文件须为 JSON 可序列化数据。composition 的 `defaultProps` 只传开关和数据路径，不传函数。

## 12.3 动画约束

遵循 Remotion 渲染规则：

- 所有动画由 `useCurrentFrame()` 驱动；
- 秒数统一乘 `fps`，不散落裸帧常数；
- 禁止 CSS transition、CSS animation 和 Tailwind 动画类；
- 所有 `Sequence` 都设置 `premountFor`；
- 使用 `interpolate` 时设置左右 clamp；
- 常规进入动画使用 `{damping: 200}` 的 spring，避免所有卡片弹跳；
- public 资源使用 `staticFile()`；
- 不在渲染过程中访问 API、读取真实用户数据或执行模型调用。

当前工程没有 `@remotion/transitions`，本集不因几个转场新增依赖。优先复用现有 `Series`、opacity 和 transform 方案。只有后续明确需要复杂转场时再评估依赖。

## 12.4 建议视觉组件行为

### `PersonaComparison`

- 三栏固定布局；
- 同一用户消息复制到三栏；
- 回复按音频时间逐句展开；
- 支持突出“礼貌回应/稳定骨架/完整动作”，不显示胜负图标。

### `BehaviorAnatomy`

- 情景、反应、例句三个区域依次展开；
- 用一根动作路径连接，不使用树状代码图；
- 例句以聊天气泡出现，不以 JSON 代码块出现。

### `DecisionGate`

- 统一 props：`label`、`question`、`method`、`status`、`color`；
- `status` 仅允许 `idle/hit/miss/checking`；
- checking 状态不要使用无限旋转动画，使用帧驱动的短脉冲。

### `InjectionTrace`

- 左：输入批次；
- 中：判别器与被点亮的文件；
- 右：messages 栈；
- 下：未命中灰色区；
- 画面最终必须停留至少 2 秒，让观众看清完整结果。

### `HazelAvatar`

- 只控制立绘位置、裁切、轻微呼吸和表情贴片；
- 不常驻；
- 不做持续上下漂浮；
- 不遮挡字幕、代码和 messages。

## 13. 配音、字幕与声音设计

## 13.1 GPT-SoVITS

全片使用灰泽满声音。旁白拆成短行：

- 单行建议 2.5～6 秒；
- 一句只承担一个信息点；
- 避免一条音频超过 12 秒；
- 技术名词前后加自然停顿；
- “system prompt”“behavior”“messages”等英文第一次出现时配中文字幕解释。

不要在 Remotion 中使用 `toneFrequency` 伪造情绪。需要情绪差异时，通过参考音频、TTS 参数或原始生成解决。

## 13.2 文件路径建议

为了不覆盖旧样片，第一集单独存放：

```text
video/public/audio/ep01/<line-id>.wav
video/public/subtitles/ep01.srt
video/narration/ep01.csv
video/src/episodes/ep01/ep01-narration.json
```

现有导出、TTS、音频对齐脚本需要增加 episode 参数，不能继续只读写根级 `narration.json` 和 `public/subtitles.srt`。

## 13.3 字幕

- 最多两行；
- 每行尽量不超过 22 个中文字符；
- 不逐字高亮整段技术旁白；
- 只对核心词做短高亮：`人格`、`事实`、`现场`、`常驻`、`关键词`、`向量`、`LLM`、`messages`；
- 字幕不得覆盖 messages 面板的关键内容；必要时场景级调整字幕位置。

## 13.4 音效

可使用少量：

- 文件卡放下的轻触声；
- Gate 命中的短提示音；
- 未命中的轻微钝响；
- QQ 气泡发送声；
- 语音条出现声。

同一场景不要堆叠多个明显音效。音效音量必须低于旁白，且不能依赖音效才能理解画面。

## 15. 实施顺序

### Phase 0：冻结证据

1. 记录制作时 commit；
2. 运行三板对照并保存全部原始输出；
3. 构造虚构 full-trace fixture；
4. 用真实代码生成 trace 与最终 messages；
5. 人工核对每个命中是否与代码一致。

此阶段完成前不要正式写动画。否则画面会围绕假数据搭建，后面只能返工。

### Phase 1：旁白与低保真 animatic

1. 按十个 scene 写旁白；
2. 导出临时 TTS；
3. 只用灰框、文字和时间轴完成 animatic；
4. 确认 10 分钟内节奏与信息密度；
5. 再决定正式标题和封面。

### Phase 2：公共视觉模块

1. 文件卡；
2. message 卡；
3. 三分类地图；
4. 四种 Gate；
5. 灰色未命中区；
6. 立绘与字幕安全区。

### Phase 3：逐场景实现

顺序按风险而不是时间轴：

1. `cold-open`：验证三栏语音与布局；
2. `full-trace`：验证最复杂的链路动画；
3. `four-gates` 与 `content-forms`；
4. system/behavior 两段；
5. 转场、开头和结尾。

### Phase 4：正式配音与对齐

1. 生成全部 HZM-SPEAK 音频；
2. 生成时长报告；
3. 根据真实音频调整 narration 时间轴；
4. 导出 SRT；
5. 重新渲染 animatic；
6. 只在时间轴稳定后添加音效和细节动画。

### Phase 5：质量检查

1. 先渲染 0.5 倍预览；
2. 抽查十个章节交界帧；
3. 检查字幕溢出；
4. 检查音频首尾是否被切；
5. 检查 trace 与真实 JSON 一致；
6. 最后渲染 1080p。
