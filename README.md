# 灰泽满（Hazel）· 基于素材驱动的 LLM 角色一致性对话框架

一个把「让 LLM 稳定还原一个真实人物的说话方式」这件事做到极致的工程实践。

表面看，它是一个虚拟主播"灰泽满"的 QQ 聊天机器人（NoneBot2 + OneBot V11 + NapCat）。但这不是一个套壳聊天 bot——**它的核心是一次系统性的角色一致性工程**：从真实直播语料蒸馏人格数据 → 多路检索按需注入 → 分层提示词组装 → 记忆系统 → 感知与真人节奏 → 评测闭环。

> 一句话：**不是靠模型的聪明，而是靠数据、检索、记忆、评测这套体系的构建，让一个 LLM 从"会聊天"变成"像某个人"。**

**一眼了解：** **54** 真实用户 · **六路**语义检索 · **三层**记忆 · **431** 单元测试 · **480+** 条人格数据 · **承诺记忆** · **会开口说话（GPT-SoVITS 语音）**

## 为什么做这个

给真实主播灰泽满做一个 QQ 聊天机器人——目标不是"能聊天"，是"**像她**"。

核心挑战很朴素：LLM 默认的"AI 腔"和真人差得太远。而"像一个人"这件事，**靠提示词堆规则是没用的**——这一条，是我在反复看着模型"聊着聊着就变回 AI 腔"、一遍遍推翻重来之后，才真正确信的。这个仓库记的就是我从"让它能回消息"到"让它像她"这一路踩过的坑、验证出来的方法，以及一套可复现的体系。

## 核心方法论（项目的最大价值）

这些不是教科书理论，是踩过坑后验证出来的：

1. **样本 > 规则**：真实对话示范"怎么说话"，比规则规定有效得多。few-shot 看样本学说话，而不是读规则学说话。
2. **素材层解决，别用提示词打补丁**：措辞、括号、重复问题从素材层根治；提示词硬约束是堆砌，无效且走老路。
3. **直播 ≠ 聊天**：直播语料必须经"转聊天"转化，且切分压缩（一个独立意思 = 一条 15-50 字短回复），不能整段保留。
4. **行为 > 标签**：人格标签（"乐观的悲观主义者"）是 tell，模型会当行为模板过度执行；要写"在什么情境怎么反应"。
5. **提示词不放具体台词**：带引号的原话放提示词 = "点名口癖 → 每条都加"；例句下沉到行为/措辞/样本层（条件注入 + 真人原话）。
6. **先筛选后分析**：从素材提炼前先判噪声（礼物/寒暄/转述），只提炼高质量话轮。
7. **确定性兜底，只在模型默认习惯压不住时才上**：括号、省略号、"她"自指，都是提示词管不住之后靠输出后处理（clean_reply）兜底。
8. **每步产物先展示审批**：不一次性跑完流水线，验证通过再往前。

## 架构演进：从"读规则"到"建体系"

这个项目是一步步进化来的——每一版都在解决一个真实暴露的问题，而不是为了加功能而加。

### V1 — 样本 few-shot
发现"读规则学说话"不行 → 改为"看样本学说话"。精选真实对话样本注入，替代提示词里的行为描述。

### V2 — 砍提示词
系统提示词从 318 行/3.2 万字砍到 40 行/3500 字。删掉数字配额与语气词详解，只保留核心人格。实测灵性明显提升——**提示词不是越多越好**。

### V3 — 多路融合检索
corpus（直播记忆）/声音样本/行为触发/措辞指纹四路向量检索 + RRF 加权融合 + 预算截断；后续版本加入偏好/核心记忆，现为六路检索。全程只调 1 次 embedding。这是"按需注入"的雏形。

### V3.1–V4 — 措辞指纹库 + 数据扩充 + 参数调优
"同一意思 → 她真实说过的原话"（被夸→"也没有啦"）；样本库 14→56 条全场景均衡；当时 corpus 273 条；承诺记忆（跨会话记住答应过的事）。

### V5 — 感知增强 + 真人节奏
时间/农历/天气感知（按用户记城市）；glm-4.6v 看图（图片→描述注入）；B站开播/动态联动推送；读秒窗口 + 分批发送（真人打字感）。

### V5.1–V5.5 — 人格工程收敛
偏好第 5 路语义检索、核心记忆层、会话级记忆（话题追踪）、行为规则样板化（带真人示范）、表情消息处理、身份分层（人设 × 真实经历）、符号纪律、去标签化。当时测试从 150+ 涨到 160+。

### 2026-08 — 从"调参数"到"建体系"
这一阶段不再是加数据，而是**承认 embedding 的边界，把判断权交给 LLM，并给调参建评测**：

- **行为 L3（LLM 意图分类）**：embedding 按句式聚团，把"灰泽满你唱歌好听"（夸）和"灰泽满你怎么又迟到"（质问）这类同句式消息挤在一起，余弦匹配把夸奖误判成质疑。治本：行为归属从 embedding 改为 LLM 判定 + 判别词兜底。
- **corpus 关键词门**：问句 vs 陈述式嵌入有天然鸿沟，纯 cosine 无法用单一阈值同时区分"相关 0.51"和"无关 0.62"。加区分性词重叠门，阈值才敢降。
- **记忆健壮性**：null 字符串污染根治、提取 JSON 修复 + 重试，记忆不再漏记/污染。
- **检索评测工具**：建标注集量化每路命中率，**把阈值调参从"人肉肉眼"变成可测量的回归**。

### 2026-09 — 群聊整场 + 语音开口 + 对话记忆的诚实

- **群聊整场参与**：读秒窗口改按"群"开会话，群内多人发言攒同一窗口，bot 参与整场群聊，而不只是跟单个人一问一答。
- **语音回复（GPT-SoVITS）真正落地**：bot 会"开口说话"了——触发规则＝成句(≥30字)朗读成语音条，成功即不再刷文字（失败自动回退文字）；短寒暄（晚安/辛苦啦）可突破下限；**含内心戏括号（小声/心虚/捂脸）一律纯文字**（TTS 表达不了）。NapCat `file://` 直发 wav 实测可用。**踩坑沉淀**：参考音频必须"无尾静音"（带尾静音的 ref 会让合成退化出"几个字 + 十几秒空尾"）；api 默认 `cut5` 分段会吞句，改整句（`cut0`）合成；合成后自动裁首尾静音。
- **对话记忆的诚实**：背景记忆 guard 细化——被问"怎么又迟到/又鸽"时大方认领老毛病（"灰泽满迟到还要理由？"），**不拿某次具体旧记忆（"那次和谁连麦"）编当下的因果**。
- **人格一致性收尾**：提示词开头定调"**你就是灰泽满本人**"（别滑进写她旁白的口气）；"她/他"自指替换折中化——只处理带自称名的复指，不再误伤真指别人的第三人称；注入记忆里的"灰泽满……她说……"当转述材料，别原样搬。
- 工程：`启动.bat` 一键起 bot + GPT-SoVITS；记忆可一键清空换新开聊。单元测试 194→243。

### 2026-09-26 · 四处修复的落地细节

（这四处在下面 09-25 那条里被合并记成了"其他修复"，这里补上具体修法与实测数）

- **表情包冷却失效的修法**：状态原来挂在会话窗口上（窗口空闲即销毁 → 每轮重建、每轮重置），改为按 `target_id` 的模块级 `_sticker_state`；`avoid_ids` 同时从"最近 3 条"扩到全部最近发过的（`STICKER_RECENT_KEEP=8`）——用户报的是"**同类**太频繁"，换个话题回来还会撞上同一张。
- **转发原文读不到（层级错）**：`orig` 在 **item 顶层**，代码查的是 `module_dynamic["orig"]`；改成顶层 + **递归**（可能是嵌套转发），拼成 `{她写的话}（转发自：{原文前 150 字}）`。
- **群聊点名 → 确定性放行**：`_addressed_to_her()` 命中（灰泽满/hzm/小满/满姐/满宝/满哥）直接接，**不调 LLM**——能确定的事不该多一次判错的机会。
- **主动发言"邀约丢失"的实测**：同一条动态各跑 3~4 次，修前 3 条里只有 1 条带邀约，修后 4/4 都带（"明天来玩…"/"要不要一起来"）。**但这是概率改善不是保证**（提示词约束的老毛病）；真要保证信息不漏得做成两步（先抽要点、再用她的口气说），先不拆，观察真实效果。测试 528→534。

### 2026-09-17 ~ 09-18 · 微博"读不到"的两层坑：负数的 ok，和顶掉新 cookie 的旧 jar

- **09-17 误报"该 UID 暂无微博"**：微博的失败码是**负数**（-100 = 未登录/被风控），而代码写的是 `if not data.get('ok')`——`not -100` 是 `False`，**错误分支被整个跳过**；跳过之后 `data` 是 null → 列表空 → 报成"该 UID 暂无微博"，**把排查方向带偏成"她没发微博"**。顺带发现未登录时登录态藏在 **body 的 `url`** 里（不在 302 的 location 头，原来只查 location 的"Cookie 失效"提示**永远不会触发**），现在两者都认，且措辞里特意带"登录"二字好让节流提示能识别。空列表也不再断言"暂无微博"，改成"多半是风控限流"。测试 422→425。
- **09-18 "换了 cookie 还是不行"**：`_load_jar` 是 `base = .env cookie → base.update(jar)`，**jar 优先级更高**（本来是为了接住微博续期下发的 `Set-Cookie`），于是**旧 jar 里那份失效会话把新填的 cookie 整个顶掉**——实测 9 个键（SUB/WBPSESS/XSRF-TOKEN/ALF/PC_TOKEN…）**一个都不是新值**，换几次都没用。
- 修法：jar 存一份"**基于哪份 .env cookie 续期**"的指纹 `_base_fp`，指纹对不上就**整份忽略、回到 .env 的值**；旧格式（扁平 dict、无 `_base_fp`）一律视为过期，安全迁移。实测修复后 9/9 个键都来自 .env，真实拉取成功。测试 425→431。
- 顺带把三轮深度调研归档成 `调研-角色对话AI架构.md`（含**证据强度分级**与行动清单）。

### 2026-09-25 · 群聊不再"有话就接" + 表情包 / 合并转发 / 主动发言 + 检索层体检

**四个原始问题（都是真实聊天里咬到人的）**

- **用几个月前的记忆回答当下**：问"今天为什么不直播"，她答"搬家的事还没弄完"——而搬家出自 80 天前那场。
  根因**不是**检索排序，是 `voice_samples` 是**唯一以 assistant turn 注入的通道**（"她本人的话"）——
  同一个事实从 corpus（system 说明）进来说 0/5 被采用，从 samples 进来 3/5。
  → **素材本土化**：16 条样本里"某一回的具体情境"改写成"她一贯如何"（实测 3/5 → 0/5）。
  判据：**样本携带的情境越具体越危险**——"明天要搬家"会被当成现在。
- **群里"有话就接"**：新增 `group_gate.py`——攒批安静下来时先判"这批要不要开口"。
  判据由用户标定：**①明确问她 → 必接 ②有情绪表达（纯情绪也算）→ 可以接 ③分享经历 → 偶尔 ④纯事务/附和/收尾 → 不接**。
  ⚠️ 判定粒度必须是**批**不是单条（逐条判会"蹭余温"：情绪一出现后面每条都靠它的余温被判该接）。
  **点名了她 → 确定性放行，不调 LLM**（能确定的事不该多一次判错的机会）。
- **同话题回复高度同质**：14 条回复里 8 条以"呃，"开头——而 86 条真实素材里**0 条**这么开头。
  根因是 `behaviors.response` **写死了措辞**（"'呃…'起头"），而注入端写着"**请严格按此模式回应**"。
  → response 只描述"**做什么**"，不描述"**用哪个词**"（措辞是台词，归 samples 承担）。实测 10/10 → 0/10。

### 2026-09-15 · 语音"转出来了但没发出去"（插话取消把它打断在合成中间）

- **现象**：TTS 明明合成了，消息却没发出去；而且**时有时无**。
- **根因（用户猜对了方向）**：`send_voice` 里 `await _synthesize()` 要几秒（GPU），
  而 `enqueue` 在收到新消息时会 `win.task.cancel()` 把正在跑的 `_flush` 打断。
  如果这几秒里用户插话 → `CancelledError` 在 await 处抛出 → 它是 `BaseException`，
  **`except Exception` 抓不到** → `_flush` 直接死掉：**wav 已经写进缓存、消息没发出去，
  文字兜底也不会走**——她那边什么都收不到。是否中招，取决于插话有没有落在合成那几秒里，
  所以"时有时无"。
- **修法**：给语音那一步加 `asyncio.shield` —— **合成+发送一旦开始就让它做完**。
  语义上也说得通：文字分段是"发一段是一段"（插话打断剩下一段是设计如此），
  而语音是一条整消息，所以"已开始 = 第一段已发出"。
  另加一道前置判断：**起跑后若已被新消息取代，就别再占 GPU 去合成**（合成完也送不出去）。
- **顺带修的一处不规范（未必是这次的元凶）**：`_to_qq_voice` 拼的是
  `file:///{Path.resolve()}`，Windows 上 `resolve()` 给的是**反斜杠**，于是发出去的是
  `file:///D:\a\b.wav`——不是合法的 file URL。接入方案「三.4」当初试通的是正斜杠版，
  实现时漏了 `.as_posix()`，现在补上。
  **但要诚实说：它大概率不是本次的原因**——路径格式是确定的，若它致命就该"一条语音都发不出去"，
  而实际是"有的发出去、有的没发"。（NapCat 对反斜杠似乎是容忍的，修它主要是回到当初验证过的形态。）
  另外失败日志现在会把实际发出去的 `file=` 打出来，下次一眼能看出。

### 2026-09-15 · QQ 内置表情识别补全（"QQ表情6" → "害羞"）

- **现象**：有些 QQ 内置表情她看不懂——消息变成 `[表情：QQ表情6]`，模型只能瞎猜"可能是无语、尴尬或调侃"。
- **根因**：`__init__._extract_face_text` 优先读 NapCat 给的 `raw.faceText`（如 `/害羞`，这是首选，连最新的超级表情都覆盖）；**但实测有些消息拿不到 faceText**，只剩一个裸 id，于是退化成 `QQ表情6`。
- **修法**：加一张 **face id → 中文名** 的兜底表（248 条），`QQ_FACE_NAMES` 查得到就用名字。
- **表从哪来（重要，别手抄）**：直接从 **QQ 客户端自己的表情配置**提取——
  `<QQNT>/resources/app/resource/default-emojis/default_config.json`。
  **关键坑**：提取规则是 `face id = qzoneCode - 100`（经典小黄脸）/ `qzoneCode - 10000`（新表情），
  **不能用配置里的 `emojiId`**——那是面板自己的编号，跟消息里的 face id 不是一回事：
  配置里 `emojiId=0` 是"惊讶"、`14` 是"微笑"，而消息里 **0=微笑、14=惊讶**（正好相反）。
  一开始按 emojiId 提差点就把表情认反了。
- 覆盖：经典小黄脸 88 条 + 新表情 160 条；查不到的仍退回 `QQ表情{id}`。

### 2026-09-15 · LLM 响应解析加护栏（`choices: null` 不再抛看不懂的错）

- **现象**：会话记忆、行为意图分类、长期记忆提取**同时**报 `'NoneType' object is not subscriptable`。三个不同模块同一句话，完全没法定位——其实是**同一个上游形状问题**。
- **根因**：9 个调用点都直接写 `resp.choices[0].message.content.strip()`，**只在"响应形状永远正确"时才成立**。上游偶发返回 `choices: null`，这句就炸成看不懂的样子。（而且 `generate_reply` 有 try/except 兜底，它失败时**不报错**，是把异常原文塞进回复发给用户——所以"只有三个报错"其实是四个都挂了。）
- **顺带堵住一个更危险的静默坑**：`deepseek-flash` **默认开思考模式**（实测：不传 `thinking:disabled` 时 `content` 是**空串**、`finish_reason=length`、`reasoning_tokens` 吃光 `max_tokens`）。以前这种情况 `.strip()` 不报错，**静默返回空串**——记忆提取/行为分类会当"这次没结果"处理，**功能悄悄失灵、日志上什么都看不到**。
- **修法**：新增 `config.extract_chat_content(resp)`，把三种坏形状（`choices` 为 None/空、`content` 为 None、正文为空）统一翻译成人话，9 个调用点全部改用它。调用方本来都有 try/except，所以**降级行为不变，只是错误能看懂了**。
- 另：`generate_reply` 的兜底回复不再把异常原文拼进去（那是内部信息，会原样发给 QQ 上每个用户），改成打日志 + 只回一句"哎呀，hzm脑子卡了一下……"。
- **诚实说明**：这个偶发**没能复现**——事后单发、按生产的 6 组参数逐条发、8 路并发发，全部正常。所以修的是**脆弱性**（同样的形状再来时能一眼看出），不是"某个必然触发的 bug"。
- **追查后发现的第二个 bug（确定性，不是偶发）**：那一轮失败的**兜底文案被写进了短期记忆**——
  `灰泽满：哎呀，hzm脑子卡了一下……（错误: 'NoneType' ...）` 成了"她说过的话"，还会作为 few-shot 喂回去。
  **一次上游抖动 = 一份永久污染**。现在 `generate_reply` 的兜底文案由 `is_fallback_reply()` 识别，
  命中就**整轮不记**（短期 + 长期都跳过）——兜底照常回给用户，只是不再当成她说过的内容。
- 顺带确认了它**不是用户数据触发的**：出事的那个用户记忆卡 1KB、历史 250 字，内容也全是正常的人格观察，
  没有会触发审核的东西；全库扫描只有这 1 条，时间点集中在 03:52 那一轮。

### 2026-09-12 · 【一致性规则】改成"只管事实"（旧文案是错误放大器）

- 旧文案：「解释同一件事时**借口要与之前保持一致**，不要前后矛盾」——**这是直接教它复读**。
  本意是防"前后矛盾"，实际效果却是把**第一次的随机选择**变成**永久设定**，已经咬过两次：
  **"威严"复读**（第一次用了"威严"，规则就要求之后都用它）和**"搬家"用了一周**
  （近况过期后本该换说法，规则让它继续一致）。而且规则原文只管"**借口**"这类事实性解释，
  模型却把它泛化到了**立场/态度**上。
- 改成【**别自相矛盾**】：**只管事实别打架**（说过的原因、安排、答应过的事下一轮别改口成另一套），
  **明确不管说法和态度**，并直说"**宁可换个方式说同一件事，也别逐字复读**"。
- 顺带补了旧【防复读】的一个漏洞：它的豁免条件是"**用户没有主动追问时**"——而用户反复追问
  正是复读高发场景，等于**在最需要它的地方自动失效**（"威严""搬家"都是被反复追问时复读的）。
  现在改成"可以正面回答，但换个说法、别把上轮那句原样搬出来"。
- 这样提示词就和代码兜底对齐了：`is_echo_reply`（整句级、窗口 8、3 次重试 + 每次校验）本来就是
  在拦"逐字重复"。

### 2026-09-12 · 事实类通道的时效（"搬家"被当了一周的理由）

- **被问"为什么又迟到/不直播"时，她总答"在收拾搬家"——因为一条过期近况被当成了当前事实。**
  `schedule.json` 的「近况」是"这周在收拾搬家"，更新于 **09-05**；到 09-12 已经 7 天，但它被**无条件注入**，只在文本里附一句"（更新于 X，过期就忽略）"——**指望模型自己判断时效**。而模型既不知道过期阈值，也没有"今天 vs 更新日"做减法的习惯。于是它会拿它当"现在为什么没播"的理由。
- **更糟的是【一致性规则】在当错误放大器**：一旦她说了一次"搬家"，"借口要与之前保持一致"就把这个借口锁死——**错误不会自我纠正，只会自我固化**，所以一周后还在说搬家。
- **这不是孤例，是一类问题**——数据层存了时间戳、注入时全部丢掉：

  | 通道 | 存了时间 | 之前注入时 | 后果 |
  |---|---|---|---|
  | `schedule.近况` | ✅ `近况_updated` | ❌ 无条件注入 | "搬家"锁死一周 |
  | `group_memory.events` | ✅ `t` | ❌ 只取 `text` | 上周群里的事当"群内近况" |
  | `significant_moments` | ✅ `date` | ❌ 只取 `summary` | 几个月前的事当"最近的记忆" |
  | `last_seen` | ✅ | ❌ 从不注入 | ← 09-11 刚修的那个 |

- **修法（时效判断归代码，不归模型）**：
  1. `schedule` 近况加 TTL（`SCHEDULE_NOTE_TTL_DAYS = 7`，近况自己写"这周…"，一周就是自然边界）——**超期就整条不注入**，而不是"注入 + 一句警告"。过期的事实等于不存在；而 `core` 里已有的 guard 规定了"没原因就大方说不知道/打哈哈"，所以撤掉近况后她的行为是**正确**的，不是空缺。`weekly` 是 weekday 制的固定表，到周自动对，不受影响。
  2. 群近况事件、长期"最近的记忆"**注入时带上相对时间**（"3天前"/"昨天"/"1个月前"），复用同一份措辞函数。
  3. 为此加了一个按**天**粒度的 `format_day_gap()`：纯日期（`2026-09-12`）没有小时精度，复用按秒的函数会把"今天的记忆"算成"18小时前"——**假精度**。

### 2026-09-12 · 撤回动态不再重推 + 微博配图修复

- **删掉了"防措辞固化"（一个在帮倒忙的兜底）**：它统计最近几条回复里反复出现的 2 字词，命中就强制换措辞重生成。实测她 105 条回复里触发 8 次，**其中 6 次拦的是她自己的自称"灰泽满"**——她的第三人称自称是身份特征不是口癖，这个机制等于在纠正她的人设。排除自称后只剩 2 次，且拦的是"这边"这类泛词。
  删掉还有个附带理由：它是同类兜底里最弱的一个——只重生成 1 次且**不校验**（防复读是 3 次 + 每次校验），nudge 只要求"换个说法表达同一个意思"（只换词不换动作，治不了"她一直那么答"）；而"威严"那次真正修好它的其实是数据层（behaviors + 判别词）。口癖这类问题回到数据层解决：`voice_samples`/`phrases` 给她多样的真实说法去化解。
- **她撤回一条动态，bot 把昨天的又推了一遍（修 bug）**：动态去重状态里只记**一条** id，判据是"**新 id ≠ 记的那条**"。她撤回最新那条后，接口返回的"最新"退回成上一条（更旧、id 更小），与记的不同 → 被判成新动态 → **把昨天的动态又广播了一遍**。置顶/删博回退同理，微博侧有一模一样的缺陷。
- 修法：改成**水位线**——只推"比已见过的最大 id 更新"的，而不是"和上一条不同"。先实测确认了两边 id 都**随时间严格递增**（B站动态取 10 条、微博取 20 条，`id` 与发布时间严格同向），所以"更大 = 更新"成立；判据收敛成 `_bridge_common.is_newer_id()` 一处，两个桥共用。基线（prime）也改成"只升不降"，停机期间被撤回/置顶时不会把水位线调低。
- 异常数据（非数字 id）退回"不同即新"，保持老行为不倒退。

### 2026-09-12 · 微博配图修复（图终于发得出来了）

- **病根在下载那一步，不在解析**：上次修过"读 `pic_ids`/`pic_infos`"（解析确实是对的，实测能抓到图链），但图仍然发不出去——因为**下载时没带 Referer**，微博图床 `*.sinaimg.cn` 有防盗链。实测同一条图链：**不带 Referer → HTTP 403 / 238 字节；带 `Referer: https://weibo.com/` → HTTP 200 / 331KB**。
- 修法：把微博图床登记进 `vision._referer_for` 的"按图源选 Referer"分流表（那张表此前只登记了 QQ 和 B站，微博是漏的）。下载失败只打日志、不阻塞推送，所以表现是"**文字发得出去、图全丢**"。
- 教训写进函数 docstring：**每接入一个新图源，都要回来登记一次**。

### 2026-09-11 · 输出格式与记忆的时间感

- **换行归一（修 bug）**：模型偶尔写成 RP 式分段（`没有。\n\n（小声）mua又不是糖…`），会在 QQ 里显示成"一条消息里的多行"，语音也被读成上气不接下气。根因两层：`clean_reply` 从不处理换行；`split_reply` 把短句并回后走 `return [text]`，原样返回**带换行的原文**。现在断行跟在标点后 → 直接接上；跟在实词后 → 补逗号（防两句焊成 run-on）。顺带修了短碎片并回时"两句之间没有任何标点"的粘连。
- **记忆的时间感**：她以前分不清"刚才说的"和"三天前说的"。长期记忆注入 `last_seen` 间隔（这个字段一直在存、却从没注入过）；短期记忆每轮存时间戳，生成前注入一行"距上一轮多久"——**只加一行汇总，不给每行打时间戳**（要的是"知道隔了多久"这个概念，不是让她复述"3 天前"）。线上老数据（裸字符串）全部兼容，不会静默清空历史。
- **记忆回流修复**：`append_user_history` 存的是 `clean_reply` **之前**的原文（`clean_reply` 在 `chat_window` 里、`handle_chat` 返回之后才跑），所以她带换行/多括号的原始输出会进记忆、又被当作"她自己怎么说话"的 few-shot 喂回提示词——**自我强化回路**：显示端每次洗掉了，源头却一直被喂养。改为存清洗后的文本。
- **罗马音修复（数据层）**：`terms`/`behaviors` 的注入文本把名字写成「中文名 + 罗马音」粘连（`四时小路Komichi`），被问"后辈都有谁"时她直接照抄了 `Komichi`。清掉所有注入文本里的罗马音，**罗马音保留在 `aliases`**——`aliases` 只参与"用户消息里有没有这个词"的匹配、从不注入，所以用户打 `Komichi` 照样命中，她答的却是中文。
- **期数词表**：`同期`(27期) 之外补上 `前辈`(20–26期) / `后辈`(28–29期) 的等价写法，简写规律是 `<期数>+7`（277=27期、287=28期、207=20期）。**用带数字边界的 pattern，不用 aliases**——aliases 是裸子串，`27期` 会误命中 `127期`、`277` 会误命中 `12777`；原来的别名已删。
- **消除"同一件事说三遍"**：括号 / 省略号纪律原来在 3 处各写一遍（提示词讲 → core 注入再讲 → `clean_reply` 代码兜底），【行为底色】又把 6 条 behaviors 压成规则重述一遍——而**粗的那遍每轮常驻，behaviors 要命中才注入，所以模型默认照粗的演**。现在提示词只留一句指针，细则只留一层；`core` 里写死的示范台词也删了（台词归数据层）。

## 技术亮点

- **分层注入架构**：10+ 层条件注入（人设/行为/corpus/记忆/会话/措辞/样本/感知），每层管一件事，出问题能定位到具体层。
- **记忆系统**：三层（短期 5 轮 / 长期画像+承诺 / 会话话题追踪）。长期记忆卡存"印象标签（带置信度）+ 用户事实 + 承诺 + 重要时刻"，支持 supersede 作废旧信息、'null' 污染防御、拒绝提取 AI 自嗨式自我披露。
- **检索评测体系**：29 条标注集 + `retrieval_eval.py`，量化每路命中率，阈值/样本改动可回归验证。
- **人格一致性评测**：InCharacter 式大五人格开放题 + 匿名化防名字作弊，实测实名/匿名都不掉分。
- **图片与视觉工程**：QQ/B站 CDN 的 Referer 分流、rkey 时效急切缓存、格式归一化、NapCat 本地缓存兜底绕开 CDN。
- **真人节奏交互**：读秒窗口攒批 + 插话优先（发送中用户插话，取消未发送分段先回新消息）。
- **工程纪律**：431 个单元测试；方法论 + 踩坑记录持续沉淀进 ROADMAP，常驻速查在 CLAUDE.md。

## 下一步想做什么

- **主动发消息**：现在灰泽满只会"你来找我我才回"。想让她像真人一样，在合适的时机主动开口——比如隔天问你一句"昨天那件事后来咋样了"。
- **给长期记忆加"遗忘"**：真人是会忘事的。现在的记忆只增不减，长期积累会越来越"重"；想让记忆有拟人化的衰减，而不是永远记得一切。

这两个方向现在都没有真实需求、也难以测试，所以暂时没动手。但它们是"让灰泽满更像一个真实的人"这条路迟早要过的地方——等有足够真实场景能验证的时候，就是动手的时候。

再往远看，是 ROADMAP 里的终极愿景——**Agent 化**：让灰泽满从"被动应答的对话系统"走向能自己决定行动的形态，"主动发消息"就是它的第一步。

## 人格蒸馏流水线（离线工具箱）

从直播素材到人格数据的全链路：`python scripts/run_tool.py <工具>` 统一入口（17 子命令按阶段分组）。

```
【蒸馏】transcribe → clean-transcript → analyze-pace → convert-to-chat
【生成】extract-persona(→behaviors 人工审批) / mine-phrases / mine-theme
         ⚠️ generate-statements 已冷落：语料现直接对 statement_final.json 向量化，不先跑它
【向量】generate-vectors -i persona/world/statement_final.json → corpus_vectors.json
         precompute voice-samples|phrases|preferences|core-stories
【评测】regression / persona-eval / retrieval-eval
【工具】bili-check / bili-login / vision-test
不在 run_tool（独立运行）：watchdog.py（假死自愈进程）/ notifier.py（SMTP，被 watchdog 用）
                     / update_schedule.py（把周表图丢 data/schedule_inbox/ 后无参跑即 OCR 更新周表）
```

产物按阶段落盘到 `outputs/` 对应文件夹（transcribe/clean/pace/convert/mine/statements/eval），最终源数据 `persona/world/statement_final.json` → `persona/world/corpus_vectors.json`（机器人只读后者）。

> 改过 `persona/behavior/behaviors.json` / `persona/speech/voice_samples.json` / `persona/speech/phrases.json` / `persona/world/preferences.json` 后需重跑对应向量；source 与 *_vectors 缓存不同步时会用旧文本检索。

## 结语

这个项目想证明的是：**让 LLM 稳定还原一个真实人物的说话方式，是可以被系统性地工程化的。** 核心不在于模型多聪明，而在于数据蒸馏、检索、记忆、评测这套体系的构建——以及大量的、可复现的试错。

如果你在看这份 README 时想到"这不就是一个聊天机器人吗"——那它还没讲好。它更准确的身份是：**一个关于「LLM 角色一致性」这个开放问题的工程答卷**。
